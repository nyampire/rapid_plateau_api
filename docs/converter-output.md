# 変換出力の性質と、取り込みで対処できる範囲

PLATEAU の CityGML は [citygml-osm](https://github.com/yuuhayashi/citygml-osm) で `.osm` に変換され、
`plateau_importer2postgis.py` がそれを DB に取り込む。

この文書は**変換出力にどういう性質があり、取り込み側でどこまで対処できるか**をまとめる。
取り込みの規則を変えるとき、再取り込みの結果を確認するとき、変換器の挙動を疑ったときに読む。

個別タスクの設計は `docs/superpowers/specs/` にある。この文書はそれらをまたぐ恒久的な参照である。

---

## 先に知っておくこと: 融合

**変換器は、外壁の線分を共有する建物どうしを 1 つにまとめる。**
`RelationMarge.checkParts` が接触を判定し、`matomeru` が取り込む側の way を `building:part` に降格させる。
javadoc に明記された意図的な設計で、v2.3.1 から変わっていない。

この融合が、以下のほとんどの性質の原因である。融合の結果、出力にはこう現れる。

- 複数の実在建物をまたぐ**合成外形**の way が新しく作られる
- 元の建物の way は `building` から `building:part` にキーが変わる
- 両者を束ねる `type=building` の relation が作られる

**元データに `bldg:BuildingPart` は存在しない。**
変換器のソースに `BuildingPart` も `consistsOf` も 1 箇所も現れず、パーサが読むのは
`bldg:Building` と `lod0FootPrint` / `lod1Solid` / `lod2Solid` だけである。
**出力の `building:part` はすべて融合の産物であり、真の部分立体ではない。**

融合を止めると上流のテストが 8 件落ちる。relation が作られることを Issue 由来のテストが期待している。
**設計変更であって不具合修正ではない**ので、こちらから止めることはしない。

## 一覧

| 変換出力の性質 | 取り込みでの扱い |
|---|---|
| 合成外形の way が作られる | **対処済み** — 建物 ID を持たない建物 way は取り込まない |
| 実在建物が `building:part` に降格する | **対処済み** — 建物 ID があれば `building` として保存する |
| 建物の型が `building:part` の値側に移る | **対処済み** — `building` が無ければ `building:part` の値を型として読む |
| 中庭のある建物が `building:part` の multipolygon になる | **対処済み** — multipolygon は `building` / `building:part` のどちらでも建物とみなす |
| `type=building` の relation が実在しない親子を作る | **対処済み** — この relation は読まない |
| multipolygon の識別子が `gml:id` に置き換わる | **保存はできる** — 形式が混ざることを承知で保存する |
| **`outer` を持たない multipolygon が出る** | **直せない** — 保存する外形が存在しない |
| **合成外形にしか無いタグがある** | **ほぼ影響なし** — 実測で大半は他の要素にも同じ値がある |
| **余分な合成 part ができる (上流 #151)** | **未対処** — 判別する手立てが無い |

以下、「直せない」「未対処」のものを詳しく書く。

---

## `outer` を持たない multipolygon

### 現象

`type=multipolygon` の relation で、メンバーが `inner` だけで `outer` が無いものが出る。
穴だけがあって外形が無い状態なので、ポリゴンを組み立てられない。

### 実測 (周南市、名前を持つ 81 メッシュ、建物 66,319 棟)

multipolygon 161 個のうち **4 個**。うち 2 個は `name` を持つ。

県立周南総合支援学校の例では、`inner` が 4 本あり、合計面積は同じ場所の合成外形の約 1/10 だった。
4 本とも閉じた妥当なリングで、それ自体は壊れていない。

### なぜ取り込み側で直せないか

外形として使える形が出力に存在しない。

候補になるのは融合外形だけだが、**融合外形は複数の建物にまたがる**ので、
それを 1 棟の外形として保存すると「実在しない建物を保存しない」という取り込みの原則に反する。
`inner` から外形を推定する方法も無い。穴の位置は外形の形を決めない。

### 取り込みの挙動

WARNING を出してスキップする。

```
⚠️ multipolygon relation -114664 をスキップ: outer member が 0 個 (期待値 1)
```

再取り込みのあと、このログの件数を数えれば影響範囲が判る。

### 影響

その建物が DB に入らない。名前を持つ場合は名前も失われる。
実測では 276 棟の名前つき建物のうち 1 棟がこれに該当した。

**上流に未報告。**

## 合成外形にしか無いタグ

### 現象

融合すると、元の建物が持っていた `name` などのタグが合成外形の側にも現れる。
合成外形は建物 ID を持たないので取り込まれない。
そのタグが合成外形にしか無ければ、DB に入らない。

### 実測 (同上、81 メッシュ)

取り込まない way 2,673 本のうち、DB の保存対象になるキーを持つのは 2,627 本。
ただしその内訳のほとんどは `height` `ele` `building:levels` で、**合成形状の値なので捨てるのが正しい**。

建物の同一性を表すタグ (`name` / `addr:*` / `amenity` / `shop` / `tourism` / `leisure` / `landuse`) を
持つのは **117 本**だけで、そのうち **109 本は同じ値を取り込む要素も持っている**。

残る 8 本 (名前 6 種) は、上の「`outer` を持たない multipolygon」と、
かつて降格 multipolygon を落としていた不具合の合算だった。後者は解消済みである。

### 結論

**この経路の情報損失は小さい。**
合成外形を捨てる規則そのものを見直す必要は無い。

## 余分な合成 part (上流 #151)

作者は v3.0.6 で解決と回答しているが、報告者が挙げた周南市の 4 建物
(`35215-bldg-38144` / `38145` / `38147` / `38184`) で再現する。
part が 7 個 (実在 4 + 合成 3) 出力され、報告内容と一致した。

合成 part は建物 ID を持たないため、現在の取り込み規則では自動的に落ちる。
つまり**実害は出ていない**。ただし「建物 ID を持たない = 合成」という前提に寄りかかっている。

**この事実は上流に未報告。**
報告するなら「解決済みとされた挙動が再現する」という事実報告の形になる。

## 識別子の形式が要素の型で変わる

### 実測 (同上、81 メッシュ)

| 要素 | `ref:MLIT_PLATEAU` の中身 | 件数 |
|---|---|---|
| way | 建物 ID (`35215-bldg-N`) | 66,215 |
| way | 無し (合成外形) | 2,673 |
| multipolygon | **`gml:id` (`bldg_<uuid>`)** | 129 |
| multipolygon | 無し | 32 |

**multipolygon には建物 ID が 1 つも付かない。**
元データ側は欠かしていない (周南市・毛呂山町の実測でいずれも欠落 0) ので、変換の過程で置き換わっている。

### 影響

DB の `plateau_buildings.ref_mlit_plateau` 列に **2 系統の識別子が混ざる**。

どちらも一意なので、同一都市内の重複検査は成立する。
ただし `<citycode>-bldg-<n>` という形式を前提に parse すると、multipolygon 由来の行で壊れる。

2026-08-06 時点で、この列の形式を解釈しているコードは本リポジトリにも dashboard にも無い。
列は不透明な文字列として保存・読み出しされている。**新しくこの列を読むときは 2 系統あることを前提にする。**

## 本番データとの対応

本番の 137 都市は上流由来で、**変換に使われたバージョンは特定できていない**。
元の `.osm` が残っていないため、事後に確定する手立ても無い。

そのため、この文書の実測値は**自前変換 (citygml-osm 3.0.6) の出力についての値**である。
本番データが同じ比率で同じ性質を持つとは限らない。

コホート比較では、上流データも同種の不整合を同オーダーで持つ (1.67% 対 自前 3.0.6 で 1.15%)。
**再取り込みを済ませれば、この不確かさ自体が消える。**

## 再取り込みのあとに確認すること

1. `outer` 無し multipolygon の WARNING の件数
2. **同一都市内の `ref_mlit_plateau` の重複** — 重複は合成形状の混入を意味する
   (バージョンによっては合成外形も識別子を持ちうる。上流 #149 が `newOutline.removeTag` を削除している)
3. 「建物の中に建物」が 0 件になること
4. 内側リングを持つ建物が存在すること (`ST_NumInteriorRings > 0`)
5. `parent_building_id` が新規取り込み分で NULL であること

## 測り直すときの手順

変換器の挙動を自分で確かめる手順は次のとおり。

```bash
cp <citygml-osm>/conversion.json <作業dir>/     # 無いと FileNotFoundException
cd <作業dir>                                    # .gml を置く
java -jar <citygml-osm>/target/citygml-osm-3.0.6-jar-with-dependencies.jar 1st
```

- **引数はモード名** (`1st` / `2nd` / `3rd` / `4th` / `pack` / `unpack`)。ファイル名ではない。
  ファイル名を渡すとどの分岐にも入らず、**何もせず exit 0** する
- `loadDir()` はカレントディレクトリの `.gml` を全部処理する
- Java 17 が要る (11 では class file version 61 で動かない)
- 1 メッシュあたり数十秒〜数分かかる

取り込み側の挙動は、DB 接続なしで `parse_osm_file_safe` を直接呼べば確かめられる
(`tests/conftest.py` の `bare_importer` fixture が同じことをしている)。
