# 上流 citygml-osm に相談すること

PLATEAU の CityGML を OSM に変換しているのは
[citygml-osm](https://github.com/yuuhayashi/citygml-osm) である。
このプロジェクトは変換器をフォークせず、上流のコードをそのまま使う方針を採っている。
そのため変換出力の不具合は、**上流に受け入れられて初めて直る**。

この文書は、上流に持ち込むかどうかを判断するための材料をまとめる。
何が判っていて、何が判っていないかを分けて書く。

変換出力そのものの性質は [converter-output.md](converter-output.md) にある。
この文書は「上流とのやりとり」に絞る。

最終更新: 2026-08-27 (4 を追加)。上流 Issue は 2026-08-07 に本文まで読んで確認した。
4 の調査時点では Issue 一覧を読み直していない。**出す前に読み直すこと。**

---

## 現在地

未報告の観測が 4 件ある。進み方には差がある。

| 観測 | 再現 | 原因の特定 | 修正 | 相談できる状態か |
|---|---|---|---|---|
| `outer` を持たない multipolygon | できる | **できた** | **作って計測した。上流の規約にも沿っている** | **できる** |
| 余分な合成 part (#151 が CLOSED だが再現する) | できる | していない | していない | 事実報告としてなら可能 |
| Lod1Solid 由来の巨大 part | 本番データで観測 | していない | していない | まだ早い |
| **変換が落ちる (5 都市)** | **できる** | **できた** | **作って計測した。上流テストも落ちない** | **できる** |

報告しないと決めたものが 2 件ある (後述)。

### 報告を保留している理由

現象の記述だけを持ち込むと、原因の切り分けを上流にお願いすることになる。
こちらは元データも変換環境も揃っていて、ビルドして走らせる手順も確立している。
原因と修正案まで揃えてから出すほうが、受け取る側の手数が少ない。

保留を解く条件は 3 つとした。

1. 手元の citygml-osm で現象を再現できる
2. 原因の箇所をソース上で特定できる
3. 修正を当てて現象が消え、**上流のテストが落ちないこと**を確認できる

3 が満たせない場合は、不具合報告ではなく設計の相談になる。
そのときは形を変えて出すか、出さないかを改めて判断する。

## 測定の範囲と限界

**先に限界を書く。**以下の実測はすべて同じ条件で採ったもので、一般化していない。

- 対象は**山口県周南市 (35215) の 81 メッシュ、建物 66,319 棟**だけである。
  81 メッシュは、周南市の 264 メッシュのうち `gml:name` を持つものを全部選んだもので、
  その範囲では標本ではなく全数である。**他都市では測っていない。**
- 変換器は **citygml-osm 3.0.6** (master `699d933`)。素のビルドで、実験用スイッチは入っていない。
- 本番に入っている 137 都市は上流配布のデータで、**変換に使われたバージョンは特定できていない**。
  元の `.osm` が残っていないため、事後に確定する手立ても無い。
  よってこの文書の数値は「自前変換 3.0.6 の出力」についての値であり、
  本番データが同じ比率で同じ性質を持つとは限らない。

## 1. `outer` を持たない multipolygon

3 件のうち最も進んでいる。**修正まで作って計測した。**

### 現象

`type=multipolygon` の relation で、メンバーが `inner` だけで `outer` が無いものが出る。
穴だけあって外形が無いので、ポリゴンを組み立てられない。

### 実測

multipolygon 161 個のうち **4 個**。うち 2 個は `name` を持つ。

県立周南総合支援学校の例では `inner` が 4 本あり、合計面積は同じ場所の融合外形の約 1/10 だった。
4 本とも閉じた妥当なリングで、それ自体は壊れていない。

取り込み側ではその建物を保存できない。名前を持つ場合は名前も失われる。
名前つき建物 276 棟のうち 1 棟がこれに該当した。

### 原因

**当初の読みは外れた。**最初は `CityModelParser` の `gml:exterior` が原因だと考えた。
Issue #137 の重複判定で外形 way を捨てるとき `elementWay` を null にするので、
直後の `outer` 追加を通らない、という筋である。ここまでは正しい。

**ただしそれだけでは出力に残らない。**この状態は 81 メッシュで約 90 回起きるが、
そのうち 86 件は `OutlineFactory` が融合の過程で `outer` を付け直している。

**修復は既に存在していて、融合の経路にしか無いのが実際の欠陥である。**
融合されない建物はそこを通らないので、`outer` が無いまま出力に残る。これが 4 件の正体だった。

### 修正の実現可否

**部分的にできる。4 件のうち 2 件。**

`OutlineFactory` の直後に掃き出しを置く。
`outer` が無く `inner` を持つ multipolygon について、
すべての `inner` を含み**建物 ID を持つ** way を探して `outer` にする。
建物 ID を持たない way は融合外形なので使わない。

融合で修復済みの 86 件は既に `outer` を持つので触らない。

`outer` にする way は、タグを空にしてから member にする。
`ref:MLIT_PLATEAU` は relation 側に移す。
これは `OutlineFactory` がマルチポリゴンを作るときと同じ手順で、
上流 [#135](https://github.com/yuuhayashi/citygml-osm/issues/135) /
[#140](https://github.com/yuuhayashi/citygml-osm/issues/140) の規約に沿う (後述)。

実測 (81 メッシュ):

| | 修正前 | 修正後 |
|---|---|---|
| `outer` 無し multipolygon | 4 | **2** |
| way / node / relation の数 | 69,193 / 422,765 / 2,623 | **すべて同じ** |
| 上流テスト | 110 件中 4 件失敗 | **同じ。失敗するテストも同じ 4 件** |

出力の差は way 2 本 (タグが空になった) と relation 2 つ (`outer` と `ref:MLIT_PLATEAU` を得た) だけで、
node は 1 つも変わらない。
(上流テストのベースラインが 4 件失敗なのは、テストが参照する gml がリポジトリに無いためで、
コードの問題ではない。)

**パーサ側で直す案は 3 つとも失敗した。**いずれも後段の修復と衝突する。

| 案 | 結果 |
|---|---|
| multipolygon があれば常に `outer` を付ける | 内側リングの無い multipolygon まで生き残り、建物 6 件が出力から消えた |
| `gml:Polygon` の終わりで、`inner` があるときだけ付ける | 融合される 86 件に新しい way を作り、後段が差し替えたあと孤立して残る |
| 同じ位置にある既存の way を `outer` に使う | **悪化した。**4 件 → 15 件 |

### 直せない 2 件

4 件それぞれについて、全 `inner` を含む way が出力にちょうど 1 本ずつある。
建物 ID を持つのは 2 本だけで、残る 2 本は融合外形である。
融合外形は複数の建物にまたがるので、1 棟の外形にはできない。付けないのが正しい。

### 上流の規約との関係

上流 [#135](https://github.com/yuuhayashi/citygml-osm/issues/135) (CLOSED) で作者は、
自身の wiki を引いて `outer` と `inner` に `building` タグを付けないことを規約として示している。
[#140](https://github.com/yuuhayashi/citygml-osm/issues/140) (CLOSED) は、
`outer` の way が `ref:MLIT_PLATEAU` を relation と重複して持つことへの検証指摘である。

実際、現行の変換出力では **`outer` メンバー way 157 本すべてがタグを 1 つも持たない**。
これは偶然ではなく、上流が意図してそう直した結果である。

**最初の版はこれに反していた。**way を `outer` にするだけでタグを残していた。
`OutlineFactory` が同じことをしている箇所 (relation にタグを写し、way の `getTagList().clear()` を
呼んでから member にする) に倣って直した。修正後は `outer` メンバー way 159 本すべてがタグ 0 個になる。

### この修正が取り込み側に届くか

**届く。**保存段階で 2 件とも測った。

| | 修正前 | 修正後 |
|---|---|---|
| 保存 | way 由来 (`w-48` / `w-22412`) | multipolygon 由来 (`r-504` / `r-22724`) |
| `ref_mlit_plateau` | 建物 ID | **建物 ID のまま** |
| 穴の数 | 0 | **2** |
| そのメッシュの建物数 | 182 / 439 | **変わらない** |

建物 ID を保ったまま中庭が入る。**取り込み側の変更は要らない。**

タグを残していた最初の版では、ここで建物 ID を失っていた。
way 収集ループが multipolygon の `outer` になった way を twin 判定より手前で捨てるためだが、
規約に沿った版では識別子が relation 側に乗るので、この経路を通らない。

## 2. 余分な合成 part (上流 #151)

### 現象

`type=building` の relation で、単独の way が part になるだけでなく、
複数の way にまたがる重複した way も作られて part に加わる。

上流 [#151](https://github.com/yuuhayashi/citygml-osm/issues/151) は **CLOSED** で、
作者は v3.0.6 で解決と回答している。

### 観測

**手元の 3.0.6 で再現する。**
報告者が挙げた周南市の 4 建物 (`35215-bldg-38144` / `38145` / `38147` / `38184`) で、
part が 7 個 (実在 4 + 合成 3) 出力され、報告内容と一致した。

**この再現は前のセッションの記録による。今回は測り直していない。**

### 実害

合成 part は建物 ID を持たないため、現在の取り込み規則では自動的に落ちる。
つまり実害は出ていない。
ただし「建物 ID を持たない = 合成」という前提に寄りかかっている。

### 相談の形

原因は特定していない。修正も作っていない。
出すなら「解決済みとされた挙動が再現する」という事実報告になる。
再現手順と対象の建物 ID は揃っているので、報告そのものは今でもできる。

## 3. Lod1Solid 由来の巨大 part

### 現象

CityGML の `lod1Solid` (建物全体の押し出し) が、独立した `building:part` として出力されることがある。
outline とほぼ同じ位置・形状・高さ・階数を持つので、
`type=building` の relation の中で outline と巨大 part が並ぶ形になる。

OSM の [Simple 3D buildings](https://wiki.openstreetmap.org/wiki/Simple_3D_buildings) は
立体どうしが共通面を持って重なることを避けるとしているので、この形は慣習に沿わない。

### 観測

**本番 DB (12.66M outline) で約 18 万 outline (1.4%) が該当する。**

この数値は本番データのものである。前述のとおり本番データの変換バージョンは特定できていないので、
**自前変換 3.0.6 での発生率は測っていない。**

上流 [#149](https://github.com/yuuhayashi/citygml-osm/issues/149) の修正
(`lod1Solid` があるとき `lod2Solid` と `bldg:boundedBy` を無視する) は
このパターンには効かない。ローカルの jar で再現を確認している。

### こちらの対処

API の出口で filter する ([#33](https://github.com/nyampire/rapid_plateau_api/issues/33))。
outline との重心距離とハウスドルフ距離が小さいことが決め手で、
これで本物の wing (別位置の棟) と分離できる。

### 相談の形

原因を特定していない。変換器側で再現条件を絞れていない。
**まだ上流に持ち込む段階ではない。**

## 4. WAY を消すときに他のリレーションの参照を外さない

**2026-08-27 に判明。修正まで作って計測した。**
4 件のうち唯一、**変換が完走しない**。落ちたメッシュの `.osm` は 1 つも出ない。

### 現象

計画の 298 都市を一括変換したところ、**5 都市が変換段で落ちた**。
日を変えてもう一度同じ計画を流しても、**同じ 5 都市が同じ終了コードで落ちた**。
断続的な失敗ではなく、入力に対して決まった形で落ちている。

落ちるのは都市あたり 1 メッシュだけで、残りは正常に変換される。
ただし 1 枚の例外で変換器全体が exit 1 になるため、その都市は出荷できない。

### 原因は 2 つある

| 都市 | 例外 | 落ちる箇所 |
|---|---|---|
| 01205 室蘭 | `ConcurrentModificationException` | `OutlineFactory.java:32` |
| 27204 池田 | `ConcurrentModificationException` | `OutlineFactory.java:32` |
| 20201 長野 | `NullPointerException` | `OutlineFactory.java:51` |
| 27203 豊中 | `NullPointerException` | `OutlineFactory.java:51` |
| 27209 守口 | `NullPointerException` | `OutlineFactory.java:58` |

#### 甲: 反復している地図に、その反復の中から要素を足す

`OutlineFactory.relationOutline()` は 32 行目で `osm.relationMap.values()` を反復する。
ループの中から呼ばれる `createOutline()` が、221 行目で**同じ地図に**新しい
multipolygon を put する。HashMap の反復子は構造変更を検知して例外を投げる。

`relationMap.put` を呼ぶ箇所を全部洗い、このループの中で `osm.relationMap` を
変更するのは 221 行目だけであることを確かめた。
そこに記録を入れて走らせると、新しい鍵の追加が 6 回起き、
**最後の 1 回の直後に例外が出た。**

`relationOutline()` はもともと、作った relation を一旦ローカルの `map` に貯めて、
ループの外で `while (outlineRelation(map))` として流し込む書き方をしている。
221 行目だけがその作法から外れている。

#### 乙: WAY を地図から消すのに、参照を外すのは目の前のリレーションからだけ

way を消す側が、その way を参照している**他の**リレーションのメンバーを外さない。
残った参照は宙に浮き、`OutlineFactory` が `osm.getWayMap().get(ref).clone()` を
呼んだところで null に触れて落ちる。

`WayMap.remove()` に削除者のスタックを記録する診断を入れて、犯人を特定した。
**同じ形の箇所が少なくとも 2 つある。**

| 削除箇所 | 該当した都市 | 同じ位置に残る代わりの way |
|---|---|---|
| `DuplicateInnerProcessor.process:68` | 27203、27209 | **ある** (`getSamePositionWay()` が選んだ partWay) |
| `BuildingGarbage.relationRemove:78` | 20201 | **無い** (メンバー 1 個の multipolygon を畳んでいるだけ) |

`BuildingGarbage` には、id を全リレーションのメンバーから剥がす `preDeleteMembers()` が
既にある。上の 2 箇所はそれに相当することをしていない。

**1st の経路で way を地図から消す箇所は 8 つある** (`update` と `upload` の
モードを除く)。上の 2 つは実際に踏まれたことを確認した。残る 6 つは未確認である。

1 つ直すたびに次が出た (`DuplicateInnerProcessor` を直したら `BuildingGarbage` が
出た) ので、**個別に潰す方針は取らなかった。**

### 修正

3 つ当てた。甲に 1 つ、乙に 2 つである。

**甲-1 `OutlineFactory.relationOutline()` — 写しを反復する**

```java
for (ElementRelation relation : new ArrayList<>(osm.relationMap.values())) {
```

ループの中で足される multipolygon は `type=multipolygon` なので、
直後の `isBuilding()` でどのみち弾かれる。写しを反復しても訪問する対象は変わらない。
`java.util.ArrayList` は import 済みで、他に変更は要らない。

**乙-1 `DuplicateInnerProcessor` — 参照を付け替える**

way を消す前に、他のリレーションからの参照を、同じ位置に残る partWay へ付け替える。
`MemberBean.setRef()` で ref を書き換えるだけなので、メンバーの順も role も変わらない。
既に付け替え先を持つリレーションでは、重複させずに宙に浮くほうのメンバーを外す。

この処理は「両者は同じ位置にある」と判定したうえで消している元の意図に沿う。
**形が保たれるので、可能ならこちらを使いたい。**

**乙-2 `OutlineFactory` — 参照先が無いメンバーを飛ばす**

`clone()` の手前で null を検査し、飛ばして警告を 1 行出す。
`BuildingGarbage` のように付け替え先が無い場合の受け皿で、
未確認の 6 箇所にも同時に効く。

飛ばした場合、その建物のアウトラインは部品を欠いたまま組まれる。
**落ちるよりはよいが、消す側で参照を外すのが本来の直し方である。**

### 実測

| | 修正前 | 修正後 |
|---|---|---|
| 落ちていた 5 メッシュ | 5 枚とも exit 1、`.osm` 無し | **5 枚とも exit 0、`.osm` が出る** |
| 飛ばした宙に浮いた参照 | — | **20201 で 1 件のみ** (他の 4 都市は 0 件) |
| 上流テスト | 110 件中 4 件失敗 | **同じ。失敗するテスト名も同一** |

上流テストのベースライン 4 件は、テストが参照する gml がリポジトリに無いためで、
コードの問題ではない (末尾の再現手順を参照)。
素の `699d933` と修正版の両方で `mvn test` を走らせ、
`CitygmlFileTest_Issue149` の同じ 4 件が落ちることを名前まで突き合わせた。

出力が変わらないことの確認は、**バイト比較**で取った。
先に「素の jar を同じ入力に当て直すと元の `.osm` とバイト一致する」ことを確かめて、
出力が再現することを対照として押さえたうえで、修正版を当てている。

| 突き合わせた成功メッシュ | 41 枚 (27203 と 27209 の 30MB 未満すべて) |
|---|---|
| バイト一致 | **41 枚** |
| 相違 | **0** |
| 飛ばした参照 | **0 件** |

**標本の限界を書いておく。**41 枚は 2 都市のもので、30MB 未満に絞っている。
298 都市の全体では測っていない。
落ちていた入力の側でしか経路が変わらないという読みと矛盾しない、という程度の確認である。

### 上流に出すときの形

甲-1 は 1 行で、意味を変えず、出力も変えない。**単独で出せる。**

乙は、消す側で参照を外すのが本来の直し方だが、
`BuildingGarbage` のように付け替え先が無い箇所では
「参照ごと消す」のか「参照が残っているうちは消さない」のかを決める必要がある。
**これは設計の判断で、こちらでは決められない。**

乙-2 (読む側で飛ばす) は対症療法である。
落ちなくなるが、欠陥そのものは残る。手元を進めるために採った。

出すなら、甲-1 を不具合報告として、乙を設計の相談として、別々に出すのがよさそうである。

### 未確認

- **way を消す残り 6 箇所**が同じ形の欠陥を持つか。踏まれたのを見ていないだけで、
  ソース上は同じ書き方をしている箇所がある
- 乙-2 が飛ばした 1 件で、**その建物のアウトラインが実際にどう欠けるか**。
  警告の件数しか見ておらず、出力の形を目で確かめていない
- 5 都市以外での発生率。**落ちなければ気づけない**ので、
  宙に浮いた参照が後段の `RelationProcessor` に黙って捨てられている分は数えていない
- 甲で、put が 6 回起きて最後の 1 回だけが例外になった理由。
  HashMap の反復子は `hasNext()` で構造変更を見ないので、
  最後の要素を処理中の put は素通りする、という筋だと思われるが確かめていない

## 報告しないと決めたもの

### 融合の設計そのもの

変換器は、外壁の線分を共有する建物どうしを 1 つにまとめる。
`RelationMarge.checkParts` が接触を判定し、取り込む側の way を `building:part` に降格させる。

これは javadoc に明記された意図的な設計で、v2.3.1 から変わっていない。
融合を止めると上流のテストが 8 件落ちる。relation が作られることを Issue 由来のテストが期待している。

不具合報告ではなく設計変更の提案になるため、こちらからは持ち込まない。
取り込み側で選別する形で完結させている。

### multipolygon の識別子が `gml:id` になる — 判断を保留

これまで「上流 #150 に既出なので報告しない」と記録していたが、
**2026-08-07 に本文を読んで、この整理が不正確だとわかった。**

[#150](https://github.com/yuuhayashi/citygml-osm/issues/150) (OPEN) が報告しているのは、
4th スクリプトが relation の `ref:MLIT_PLATEAU` を `source=MLIT_PLATEAU` に変換しない、という別の問題である。
例として挙がっている値がたまたま `bldg_<uuid>` 形式なだけで、
**「値が建物 ID ではなく `gml:id` である」ことを欠陥として述べている人はいない。**

作者は同じ Issue のコメントで、v2 以前は PLATEAU のマルチポリゴン構造を正しく変換できておらず、
v3 で中空部分を `relation=multipolygon` に変換するよう修正した、と説明している。

**そもそもこれが欠陥なのかどうか、こちらでも決めていない。**

1 の修正を規約に沿わせた結果、そこで直した 2 件の multipolygon は
`gml:id` ではなく**建物 ID** を持つようになった。way から移したためである。
つまり「multipolygon は建物 ID を持てない」わけではない。
残りの multipolygon がなぜ `gml:id` を持つのかは追っていない。

## 再現手順

```bash
cp <citygml-osm>/conversion.json <作業dir>/     # 無いと FileNotFoundException
cd <作業dir>                                    # .gml を置く
java -jar <citygml-osm>/target/citygml-osm-3.0.6-jar-with-dependencies.jar 1st
```

- **引数はモード名** (`1st` / `2nd` / `3rd` / `4th` / `pack` / `unpack`)。ファイル名ではない。
  ファイル名を渡すとどの分岐にも入らず、**何もせず exit 0** する
- `loadDir()` はカレントディレクトリの `.gml` を全部処理する
- Java 17 が要る (11 では class file version 61 で動かない)
- 1 メッシュあたり数十秒から数分かかる
- ソースを変えたら `mvn clean package` で jar を作り直す。`mvn test` は jar を更新しない
- `mvn test` に `-DargLine` は効かない。pom が直書きしているので、環境変数で渡す
- 上流テストのベースラインは **110 件中 4 件失敗**。
  原因はコードではなく、テストが参照する gml がリポジトリに存在しないこと
