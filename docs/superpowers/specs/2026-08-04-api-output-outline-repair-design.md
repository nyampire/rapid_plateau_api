# API 出口での親子関係の補正（#39 の暫定対処）

- 日付: 2026-08-04
- 関連: #39（親子関係の不整合）、#41（importer の way 番号衝突の修正）、#42（親を持たない部分立体）

## 背景

#39 の調査で、外形と部分立体の親子関係に不整合がある組み合わせが本番に 43,280 件あり、
原因が2つに分解できることを本番データの全件測定で確認した。

| 不整合の型 | 件数 | 割合 | 特徴 |
|---|---|---|---|
| 別の建物への取り違え | 16,175 | 37% | まったく重ならない。重心距離は中央値 1,786m、最大 30,258m |
| 外形のほうが小さい | 21,306 | 49% | 外形が部分立体の内側に完全に入る。面積比 1.2〜5.0。外形の数では 13,661 |
| その他（部分的に重なる） | 5,799 | 13% | 面積比が 1.2 未満または 5.0 以上 |

取り違えは importer の way 番号衝突が原因で、#41 で修正済み。
ただし修正が効くのは今後の取り込みだけで、既存データは再取り込みまで残る。

外形が小さい型は変換処理に由来する。こちらも既存データは再取り込みまで残る。

当面、新しい都市を追加する予定がないため、再取り込みを待つより API の出口で流出を止めるほうが
効果が早い。本設計はそのための暫定対処である。

## 実証した前提

設計の根拠は本番データの測定に置く。推定で設計しない。

**取り違えが importer 由来であること（全 16,175 件、抽出なし）**
部分立体が実際にどの外形の内側にあるかを調べると、12,594 件（78%）は別のどれかの外形の内側にあり、
そのうち 12,302 件（76%）ではその外形が取り違えられた親と同じ way 番号を持つ。
正しい親はデータベースの中に存在し、同じ番号の別物が選ばれていた。

**現在の外形が建物の輪郭になっていないこと（無作為標本 1,500 / 13,661）**
外形の面積は、その関係に属する全部分立体の和の 50%（中央値）しかない。

**入れ替えが正しい外形を作ること（同じ標本）**
最大の部分立体は、全部分立体の和を 100%（中央値）覆う。
関係内のすべての部分立体を包含するものが 1,373 件、**91.5%** にあたる。

残る 8.5% では、最大の部分立体でも全部は包含しない。この分は本設計の対象外とする。

**測定と判定条件のずれ（意図的に厳しくしている）**
上の 91.5% は「最大の部分立体が全**部分立体**を包含する」を測った値である。
後述の判定条件は、元の外形も包含対象に含めるため、これより厳しい。
条件を緩める側に倒さないのは、「適用したものは必ず正しい」を保証するためである。

**実装後の本番実測（2026-08-04、全 13,661 件、抽出なし）**
実装した条件そのままで測ったところ、適用は **12,552 件 / 13,661 件 = 91.9%** だった。

設計時には「91.5% を上回らない」と書いたが、**これは誤りだった**。
包含の要求を1つ増やした一方で、判定の母集団から「記録上の親と交差しない部分立体」を
除外している。除外されるのは遠くにあって包含できない部分立体なので、除外は包含条件を
**満たしやすくする**。この緩和が、外形を包含対象に加えた厳格化を上回った。
2つの変更が逆向きに効くことを設計時に見落としていた。

残る 8.1%（1,109 件）は入れ替えずに現状のまま出力する。

補足として、凸包で測ると最大の部分立体の被覆率は 0.856 に見える。
凸包は非凸な建物で実際の輪郭より大きく出るため、この値を判断に使ってはならない。

## 実装の結論（2026-08-04、実測を受けて変更）

**このブランチで出すのは「交差しない部分立体の除外」だけである。役割の入れ替えは出さない。**

入れ替えは実装・テストまで完了したが、本番で発火する 12,552 件の中身を測ったところ、
面積比の最大が **803 倍**、重心距離の最大が **172.9m** だった。
面積比 5.0 超が 825 件、距離 50m 超が 272 件ある。
面積比 803 倍は同じ建物の輪郭ではありえない。

原因は判定条件の性質にある。
本設計の保証は「入れ替え後の外形が関係の全メンバーを包含する」で、これは 12,552 件すべてで
成立している。しかしこれは**内部整合**であって、**正しい輪郭かどうか**ではない。
変換器は接する建物どうしを1つの関係にまとめるため、1つの関係が複数の実建物を含みうる。
そこで最大の部分立体を昇格させると、ある建物の輪郭が複数建物の外形として出力される。
包含は成立し、輪郭としては誤っている。

面積比に上限を設ける案も検討したが、上限値の根拠が「欠陥集団を記述したときの統計値」しか
無く、どこから実害が出るかを測った値ではない。閾値を足しても保証にはならない。

### 2026-08-04 追記: 入れ替えは保留ではなく「成立しない」

変換器のテスト用 GML (`50303525_bldg_6697_op.gml`、大牟田 40205) を citygml-osm 3.0.6 で
実際に変換し、元データと突合した。

| 元データ (CityGML) | 数 |
|---|---|
| `bldg:Building` | 691 |
| `bldg:BuildingPart` | **0** |
| `consistsOfBuildingPart` | **0** |

変換後の出力は way 771 本。うち `ref:MLIT_PLATEAU` を持つのが 691 本で、**元データの Building 数と
完全に一致**する。持たない 80 本は合成された way。

**元データに BuildingPart が 1 つも無いのに、出力には `building:part` の way が 157 本ある。**
つまり出力の部分立体はすべて変換器が作ったもので、CityGML 由来の建物の一部ではない。
さらに relation 45 個すべてが、複数の独立した Building をまとめている。

これは「3D 建物の外形が小さすぎる」問題ではなかった。**独立した複数の建物を 1 つの relation に
まとめ、それらを囲えていない形状を外形と称している**状態である。

最大の部分立体を昇格させれば、ある 1 棟の輪郭が無関係な複数棟の外形になる。
面積比の裾に現れた異常値 (最大 803 倍) は例外ではなく、構造の帰結だった。
**入れ替えは条件を絞っても成立しない。** API 出口でも importer でも同じで、直すべきは
「接する独立建物を 1 relation にまとめる」という変換器の設計そのものである。

限界: 1 ファイルでの確認である。前セッションが別ファイル (53391550) の CityGML で
「まとめられた建物はすべて `consistsOfBuildingPart=0`」を確認しており、2 ファイルで同じ傾向。
全都市への一般化には追加の確認が要る。

実装済みの入れ替えは `feature/api-output-outline-repair` に残してある。

## 除外だけを出す根拠

記録上の親と交差しない部分立体は、どう解釈しても親子ではない。
出力しないという対処は、誤ったものを取り除くだけで新しい判断を持ち込まない。
本番実測で 16,175 件、重心距離は中央値 1,786m・最大 30,258m。
importer 側は #41 で修正済みなので、これは既存データに対する暫定処置である。

なお NULL は落とさない。`ST_Intersects` は入力ジオメトリが NULL のとき NULL を返すが、
これは「交差しない」ではなく「判定できない」である。OSM 出力はノード列から作るので、
`geom` が壊れていてもノードが正常なら出力は正しい。判定できないことを理由に捨てると
正常なデータを失う。

## 対象と非対象

対象は2つ。

1. 記録上の親と交差しない部分立体を出力しない
2. 条件を満たす関係で、外形と最大の部分立体の役割を入れ替える

非対象。

- DB の中身は変えない
- 新しいジオメトリを作らない。既存の way の役割を入れ替えるだけ
- 上記 8.5%（最大の部分立体が全部を包含しない関係）
- 「その他」5,799 件（部分的にしか重ならない組み合わせ）
- #42 の親を持たない部分立体

## 判定（SQL）

`related_parts` に重なり条件を足し、記録上の親と交差しない部分立体を除外する。
これが対象 1 にあたる。

除外後の集合に対し、関係ごとに次を判定する。
最大面積の部分立体を P、現在の外形を O とする。

```
ST_Area(P) > ST_Area(O)
AND ST_Contains(P, ST_Union(O と P 以外の全メンバー))
```

成り立つときだけ、入れ替え対象として P の id を返す。

面積が同じ部分立体が複数あるときは、id の小さいほうを P とする。
同じ入力に対して常に同じ応答を返すためで、既存の重複排除が決定的な順序付けを使っているのと同じ考え方である。

この条件はそのまま正しさの基準である。**適用後の外形は、その関係の全メンバーを包含する。**
適用したものは必ず正しい、という保証が成立する。

包含判定は、外形より大きい部分立体を持つ関係にだけ走らせる。
通常の関係には面積比較しか発生しない。

判定の順序に依存がある。除外を先に行い、その結果の集合に対して包含を判定する。
出力しないものを包含の判定に含めると、出力される関係の内部整合と一致しなくなる。

## 修復（Python）

入れ替え対象の way は、元の外形が持っていた `building` の値で出力し、リレーションでの役割を outline にする。
元の外形は `building:part=yes` で出力し、役割を part にする。

他のタグは動かさない。
リレーション自体のタグも現状のまま、元の外形の属性を使う。
建物全体を説明する属性なので、どちらの way が外形になっても変わらない。

## 観測と撤去

1 リクエストあたりの入れ替え件数と除外件数をログに出す。

撤去条件をコードのコメントに書く。
変換側の対処と全都市の再取り込みが済み、本番で両方の該当が 0 件になったときに、この補正は不要になる。
件数をログに出すのは、その時点で「もう発火していない」を確認する手段が無いと撤去できないためである。

## エラー処理

無効なジオメトリが本番に存在する（`ST_Contains` が TopologyException で落ちる例を確認済み）。
判定では `ST_MakeValid` を通す。

判定が失敗した関係は、入れ替えずに現状のまま出力する。
補正は改善のための処理であり、失敗して応答全体を落とすべきではない。

## テスト

Python 側は DB 不要の単体テストで書く。既存の `api` fixture が辞書を直接扱う。

- 入れ替え後、対象の way が元の外形の `building` の値を持つ
- 入れ替え後、元の外形が `building:part=yes` になる
- リレーションの役割が入れ替わる
- 条件を満たさない関係は変更されない
- 他のタグが動かない

SQL 側は統合テスト（`fresh_plateau_full_schema`、PostGIS 必須）で書く。

- 最大の部分立体が全メンバーを包含する関係で、入れ替え対象が返る
- 包含しない関係では返らない
- 交差しない部分立体が除外される
- 除外の結果として包含が成立する場合に、正しく入れ替え対象が返る

## 検証

実装後、本番と同じ bbox で応答を取得し、次を確認する。

- 高知市の取り違えの例で、約 50m 四方の要求に対して 2.5km 先のジオメトリが返らない
- 入れ替えが発生した関係で、外形が全メンバーを包含する
- 形状の総数が意図した分だけ変わる（除外分のみ減り、入れ替えでは増減しない）
