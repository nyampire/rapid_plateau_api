# 座標から決まるノード id の設計

- 日付: 2026-08-12
- 関連: [#51](https://github.com/nyampire/rapid_plateau_api/issues/51)、[#38](https://github.com/nyampire/rapid_plateau_api/issues/38)（応答の中でのノード共有）、`2026-08-04-synthetic-id-scheme-design.md`（way と relation の採番）

## 背景

壁を接する 2 棟が共有する角に、Rapid が同じ座標のノードを 2 つ作り、JOSM が重複ノードとして報告する。

API はノードの id を、その応答で先に処理された建物の DB ノード行の id から決めている。

```python
canonical_id = coord_to_nid.get(key)
if canonical_id is None:
    canonical_id = -node_data['id']
    coord_to_nid[key] = canonical_id
```

DB は建物ごとにノードを持つので、共有される角には建物の数だけ行がある。
どの行が先に来るかはその範囲にどの建物が入るかで変わるため、同じ角が取得のたびに別の id で届く。

Rapid は API が返した id をそのままクライアント側の entityID にする。
別の id で届いた同じ角は別のノードになり、承認するとその 2 つがアップロードされる。

#38 は応答 1 つの中でノードを共有するようにした修正で、その範囲では今も重複が起きない。
当時のテストも応答 1 つの中だけを数えていて、取得する範囲をまたぐ場合を確かめていなかった。

## 実測した事実

**同じ角が範囲によって別の id になる。**
宇城市の (32.6445365, 130.6984598) を 2 通りの範囲で取得した。

| 応答に含まれる建物 | その角のノード id |
|---|---|
| 隣接する 2 棟とも入る | `-272155034` |
| 隣の 1 棟が入らない | `-272163761` |

DB にはこの座標にノード行が 2 つあり、それぞれ隣接する 2 棟に属している。

**共有される角は珍しくない。**
宇城市では、複数のノード行がある座標が 10,605 か所ある。
そこにあるノード行は 21,427 で、市全体 228,154 行の 9.4% にあたる。

**DB に索引を足す案は重い。**
`plateau_building_nodes` は 9,400 万行で 17GB あり、索引は `id` と `building_id` と `osm_id` の 3 つだけである。
座標に索引を張るとおよそ 3GB になり、メモリの小さいサーバでは構築も取り込み時の更新も重い。

**丸めて id を作る案は形を変える。**
座標を丸めて桁を減らすと id は小さくなるが、別々の角が同じ枡に落ちる。

| | 座標数 | 緯度 6 桁 × 経度 6 桁 | 緯度 7 桁 × 経度 6 桁 | 緯度 6 桁 × 経度 7 桁 |
|---|---|---|---|---|
| 宇城市 43213 | 217,332 | 25 | 4 | 1 |
| 新宿区 13104 | 674,243 | 1,042 | 242 | 176 |

密な都市ほど近接する角が増えるので、全国では無視できない件数になる。

**id の大きさに制約は無い。**
アップロードを受ける cgimap は仮 id を `int64_t` で読む（`osm_nwr_signed_id_t`）。
文字列からの変換は `std::from_chars` で、範囲外になるのは int64 を超えたときだけである。
作成する要素に課される条件は 2 つだけで、大きさの上限は無い。

```cpp
if (valid && op == operation::op_create && id() >= 0) {
    throw payload_error("Placeholder IDs must be negative for created elements.");
}
```

Rails 側は `xml["id"].to_i` で読むので桁の制限が無く、
「作成する要素の仮 id は型ごとに一意であること」が追加の条件になる。

**Rapid はノード id を数値として読まない。**
`osmEntity.id.fromOSM` は型の頭文字を文字列連結し、`toOSM` は先頭 1 文字を落とすだけである。
数値に変換しているのは `osmRelation.creationOrder` の 1 箇所だけで、
これは relation の並べ替えに使われ、ノードは通らない。

既存コードが挙げている「JavaScript の安全整数 9e15」は way id の桁を見積もった記述で、
`plateau_buildings.id` が SERIAL であることに由来する。ノード id には当てはまらない。

## 採番

座標だけから決める。応答に何が入っているかに依存しない。

```
lat_i = round((lat - 20.0) * 1e7)      # 0 .. 260,000,000
lon_i = round((lon - 122.0) * 1e7)     # 0 .. 320,000,000
node id = -(1 + lat_i * 320,000,001 + lon_i)
```

範囲は緯度 20 度から 46 度、経度 122 度から 154 度とする。
沖ノ鳥島 (20.4) から択捉島 (45.5)、与那国島 (122.9) から南鳥島 (154.0 手前) までを含む。

id の大きさは最大 83,200,000,580,000,001 で、int64 の上限のおよそ 111 分の 1 に収まる。

`+1` は id が 0 になるのを避けるためで、cgimap の「0 でないこと」を満たす。

### なぜ単射か

`lat_i_A × 320,000,001 + lon_i_A == lat_i_B × 320,000,001 + lon_i_B` を考える。
`lon_i` の取りうる最大値は 320,000,000 で乗数より小さいので、商と余りが一意に決まる。
したがって `lat_i` と `lon_i` の両方が一致する。

単射であることは重複を防ぐためだけではない。
`PlateauService` は既に見た entityID の要素を捨てるため、
異なる座標が同じ id になると、後から来た角が黙って消えて way の形が壊れる。

### 範囲外の座標

警告を記録し、その座標だけ現行どおり DB のノード行の id を使う。

範囲外の座標は本番データには無い見込みだが、丸めた値が範囲を外れると id が他の座標と衝突しうる。
衝突は形を壊すので、id の安定性より出力の完全性を優先する。
この経路に落ちた座標は #51 の症状が残るが、警告から件数が判る。

### `coord_to_nid` の廃止

id が座標の関数になるので、「どの建物が先に来たか」を覚える必要が無くなる。
同じ `<node>` を二重に出さないための `emitted_node_ids` は残す。

## 変更の範囲

`osmfj_plateau_api.py` だけを変更する。

- 座標から id を返す純粋な関数と、範囲を表す定数を足す
- `_make_way_elem` の中の `coord_to_nid` を引く処理を、その関数の呼び出しに置き換える
- 合成 id の採番を説明しているコメントに node の規則を足す。
  現在の記述は way と relation しか扱っておらず、9e15 の目安が way id の話であることも書かれていない

DB のスキーマ、取り込み、Rapid のコードはいずれも変更しない。
147 都市の再取り込みとは独立に出せる。

## テスト

先にテストを書く。1 から 3 は #51 の受け入れ条件に対応する。

1. 同じ座標が、応答に含まれる建物の組み合わせと順序によらず同じ id になること
2. 壁を接する 2 棟が角のノードを共有すること
3. 応答の中の重複が 0 件のままであること。既存の `_josm_duplicate_node_coords` を使う
4. 座標を格子状に動かし、異なる座標が同じ id にならないこと
5. id が負で、0 でなく、int64 に収まること
6. 範囲外の座標で警告を出し、DB のノード行の id に落ちること
7. 応答から組み立てた仮 id が、cgimap と Rails の条件（負、0 でない、型ごとに一意）を満たすこと

7 は実アップロードの代わりではない。その前段で契約を固定する。

## 反映と確認

API の再起動だけで反映される。再起動には sudo が要るのでユーザが実行する。

1. 報告された 2 か所を、隣の建物が入る範囲と入らない範囲の両方で取得し、同じ id が返ること。
   今日 `-272155034` と `-272163761` に分かれた条件そのものである
2. Rapid から実際に建物を承認してアップロードし、JOSM が重複ノードを出さないこと。
   認証が要るのでユーザが実行する
3. Rapid のキャッシュに古い id が残るため、確認は再読み込みかシークレットウィンドウの後に行う

## 採らなかった案

**座標を丸めて 9e15 の目安に収める。**
新宿区だけで 176 か所の角が消える。
衝突する 2 点は必ず 11cm 以内にあるので遠い場所が混ざることはないが、形が変わる。

**DB に索引を張り、座標ごとの最小の id を引く。**
精度は落ちず id も小さいままだが、9,400 万行への索引の構築と維持が メモリの小さいサーバでは重い。
応答ごとに問い合わせが 1 つ増える。

**DB に共有ノードの正本を列として持たせる。**
id が厳密に一意になるが、移行と取り込み側の変更が要る。
再取り込みと順序を合わせることになり、先に出せない。

**Rapid の承認時に座標でノードをまとめる。**
API の採番に依存せず直るが、直るのは Rapid だけで他の利用者には効かない。
上流と共有している承認の処理に手を入れるため、道路など他のデータへの影響を確かめる必要がある。
