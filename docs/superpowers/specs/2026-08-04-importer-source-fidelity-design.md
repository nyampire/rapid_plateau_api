# 取り込みを元データに忠実にする設計

- 日付: 2026-08-04
- 関連: #39（親子関係の不整合）、#42（親を持たない部分立体）、#30（建物 ID の保存、PR #43 でマージ済み）

## 背景

変換器が出力する `.osm` には、元データに対応物のない形状が含まれる。
現在の取り込みはそれをそのまま DB に入れているため、実在しない建物が保存され、
「建物の中に建物」をはじめとする不整合の原因になっている。

本設計は**取り込み側だけ**を対象とする。変換器には手を入れない。
変換器の挙動は上流の設計判断であり、上流のテスト 8 件がそれを固定している。
こちらのペースで変えられないものに依存しない形にする。

## 実測した事実

以下はすべてローカルで変換・取り込みを実行して得た値である。推測は含まない。
使用したのは citygml-osm 3.0.6（master `699d933`、本番データと同じ v3 系）。

**変換器は CityGML の `BuildingPart` を読まない。**
ソース全体に `BuildingPart` も `consistsOf` も 1 箇所も現れない。
出力の `building:part` は、接触する建物を融合したときに作られたものである。

**合成形状は複数の実在建物にまたがる。**
飯塚 50303525 で、建物 ID を持たない `building:part` 35 本すべてが複数の実在建物にまたがる（3〜19 棟）。
同じく建物 ID を持たない外形 45 本も 2〜9 棟にまたがる。

**合成形状を取り込まなければ「建物の中に建物」は消える。**
周南 51310655（2,056 棟）で 154 組。外側はすべて合成形状で、実在建物が外側のものは 0 組。
建物 ID を持つ way だけに絞って取り込むと **0 組**になった。

**穴のある建物は `type=multipolygon` で出力され、すべて実在建物である。**
周南 10 メッシュ 13,391 棟で 15 個（0.11%）。合成形状は 1 つも含まれない。
15 個すべて、対応する建物が way 側に重複して現れることはない。

**元データは建物 ID を欠かさない。**
周南市 3 メッシュ 6,738 棟、毛呂山町 43 メッシュ 24,418 棟のいずれも欠落 0。
一方、変換器はマルチポリゴンで建物 ID を落とす（15 個中 5 個で欠落、市立小学校など実在の大型建築を含む）。
値は元データにあるので、変換器側の不具合である。

## 原則

1. **元データの建物 1 棟を、DB の 1 行に対応させる。**
2. **元データにある内側リングを保持する。** 中庭を塗りつぶさない。
3. **識別子の有無で実在と合成を判定しない。** 表現の種類で判定し、識別子は取れたものだけ保存する。

原則 3 は、変換器が実在建物の識別子を落とす場合があるために必要である。
識別子を判定に使うと、市立小学校のような実在建物を取りこぼす。

## 取り込みの判定

| 対象 | 扱い | 根拠 |
|---|---|---|
| 建物 ID を持つ way | 取り込む | 元データの建物と 1:1 |
| `building` タグを持つ `type=multipolygon` の relation | 取り込む（内側リングを保持） | 15/15 が実在建物 |
| 建物 ID を持たない way | 取り込まない | 複数の実在建物にまたがる合成形状 |
| `type=building` の relation | 読まない | 合成外形の入れ物 |

`building:part` タグを持つ way でも、建物 ID があれば元は独立した建物なので `building` として取り込む。

## 保存

`plateau_buildings.geom` は `geometry(Polygon,4326)` で、内側リングをそのまま保持できる。
実 DB で `POLYGON((外側),(内側))` を挿入し `ST_NumInteriorRings = 1` を確認した。**スキーマ変更は不要。**

`plateau_building_nodes` は建物ごとの平坦なノード列なので、2 つの環を区別できない。
環の番号を持つ列を 1 つ追加する。0 を外側、1 以降を内側とする。

親子関係（`parent_building_id`）は作らない。
`type=building` の relation を読まないため、参照元がなくなる。既存の列は残すが、新規取り込みでは NULL のままになる。

## API

内側リングを持つ建物は、`type=multipolygon` の relation として出力する。
outer と inner の way を出し、タグは relation に付ける。変換器の出力形式と同じにする。

内側リングを持たない建物は、従来どおり way 1 本で出力する。

`type=building` の relation の出力はなくなる。親子関係を保存しないためである。

## 対象外

**変換器の修正。** 融合を止める案は上流のテスト 8 件を壊す。上流の設計判断であり、本設計では扱わない。

**三角形の建物が除外される不具合。** 別 Issue とする。
面積の検算が度の二乗で行われており、閾値 `1e-6` は緯度 34 度で約 10,190 m² に相当する。
三角形（頂点 3 つ）の建物だけこの検算を通るため、1 万 m² 未満の三角形がすべて除外される。
周南 51310655 で 16.4 m² の建物 1 棟が実際に落ちていた。原因も対処も本設計と独立している。

**既存データの是正。** 本設計は新規取り込みにのみ効く。既存の 1,489 万棟は再取り込みまで変わらない。

## 未解決

**本番データとの対応が未実測である。**
本番 137 都市は上流由来で、変換器のバージョンは v3 系という以上に特定できていない。
本番の relation が複数の建物 ID を束ねているかは、`ref_mlit_plateau` が入った再取り込み後に確認する。

**変換器がマルチポリゴンで建物 ID を落とす件を上流に伝えていない。**
上流に #150 が OPEN だが内容が異なる可能性がある。別途確認する。

**穴のある建物の割合は 1 都市 10 メッシュの実測である。**
0.11% は周南市の値で、都市による差は測っていない。

## 検証

取り込み後に次を確認する。

- DB の建物数が、元データの `bldg:Building` 数と一致する（三角形の不具合を直した後）
- 「建物の中に建物」が 0 件になる
- 内側リングを持つ建物が DB に存在する（`ST_NumInteriorRings > 0`）
- API の応答で、穴のある建物が `type=multipolygon` として返る
- `parent_building_id` が新規取り込み分で NULL である
