# 取り込みを元データに忠実にする設計

- 日付: 2026-08-04
- 関連: #39（親子関係の不整合）、#42（親を持たない部分立体）、#30（建物 ID の保存、PR #43 でマージ済み）

## 背景

変換器が出力する `.osm` には、元データに対応する形状のない way が含まれる。
現在の取り込みはそれをそのまま DB に入れているため、実在しない建物が保存され、
「建物の中に建物」の原因になっている。

本設計は**取り込み側だけ**を対象とする。変換器には手を入れない。
変換器の挙動は上流の設計判断であり、上流のテスト 8 件がそれを固定している。
こちらのペースで変えられないものに依存しない形にする。

## 実測した事実

すべてローカルで変換・取り込みを実行して得た値である。
使用したのは citygml-osm 3.0.6（master `699d933`、本番データと同じ v3 系）。
対象は周南市（山口県 35215、2024年度 v4）の 10 メッシュ、建物 way 13,391 本。

**変換器は CityGML の `BuildingPart` を読まない。**
ソース全体に `BuildingPart` も `consistsOf` も 1 箇所も現れない。
出力の `building:part` は、接触する建物を融合したときに作られたものである。

**建物 ID を持たない建物 way は、すべて元データに対応しない。** 386 本すべてで確認した。
375 本は複数の実在建物にまたがる（2〜19 棟）。
9 本は `type=multipolygon` の `inner` メンバー、つまり穴である。
残る 2 本は元データの `lod0FootPrint` と頂点が 1 つも一致しない。
うち 1 本は `name=市立秋月小学校` を持つが、形状は元データに存在しない。融合結果にタグが移ったものである。

**穴のある建物は `type=multipolygon` で出力され、すべて実在建物である。**
15 個あり、合成形状は含まれない。対応する建物が way 側に重複して現れることもない。

**変換器はマルチポリゴンで建物 ID を落とす。** 15 個中 5 個で欠落し、市立小学校など実在の大型建築を含む。
元データ側は欠かしていない（周南市 3 メッシュ 6,738 棟、毛呂山町 43 メッシュ 24,418 棟のいずれも欠落 0）。

**本設計の規則で取り込むと「建物の中に建物」が消える。**
2 メッシュ 3,829 棟で 0 件。同じデータを現在の規則で取り込むと 155 件（51310655 で 154、51310636 で 1）。

## 原則

1. **変換出力にある実在建物 1 棟を、DB の 1 行に対応させる。**
   比較対象は変換出力である。元データと変換出力の差は変換器の責務であり、本設計では扱わない。
2. **元データにある内側リングを保持する。** 中庭を塗りつぶさない。
3. **識別子が欠けていることを理由に、実在建物を捨てない。**
   マルチポリゴンでは実在建物でも識別子が落ちる。識別子は取れたものだけ保存する。

## 取り込みの判定

| 対象 | DB での扱い |
|---|---|
| 建物 ID を持つ way | 1 行の建物として保存する |
| 建物 ID を持たない建物 way | 保存しない。元データに対応する形状が無い合成物なので破棄する |
| `building` タグ付き `type=multipolygon` の relation | 1 行の建物として保存する。outer を外側リング、inner を内側リングにする |
| その `inner` メンバーの way | 独立した建物としては保存しない。上記の内側リングとして保存する。付いている `building:part=yes` は使わない |
| `type=building` の relation | 親子関係を作らない。メンバーの way は上の規則で個別に判定する |

`building:part` タグを持つ way でも、建物 ID があれば元は独立した建物なので `building` として保存する。

現在の取り込みとの違いは 3 点ある。
合成形状を保存しなくなる。
`inner` の way が独立した建物ではなく穴になる（現在は中庭が建物として保存されている）。
親子関係を作らなくなる。

## 保存

`plateau_buildings.geom` は `geometry(Polygon,4326)` で、内側リングをそのまま保持できる。
実 DB で `POLYGON((外側),(内側))` を挿入し `ST_NumInteriorRings = 1` を確認した。**スキーマ変更は不要。**

`plateau_building_nodes` は建物ごとの平坦なノード列なので、2 つの環を区別できない。
環の番号を持つ列を 1 つ追加する。0 を外側、1 以降を内側とする。

`parent_building_id` は新規取り込みでは NULL のままになる。列は残す。

## API

内側リングを持つ建物は、`type=multipolygon` の relation として出力する。
outer と inner の way を出し、タグは relation に付ける。変換器の出力形式と同じにする。

内側リングを持たない建物は、従来どおり way 1 本で出力する。

`type=building` の relation の出力はなくなる。親子関係を保存しないためである。

## 対象外

**変換器の修正。** 融合を止める案は上流のテスト 8 件を壊す。上流の設計判断であり、本設計では扱わない。

**三角形の建物が除外される不具合。** 別 Issue とする。
面積の検算が度の二乗で行われており、閾値 `1e-6` は緯度 34 度で約 10,190 m² に相当する。
三角形（頂点 3 つ）の建物だけこの検算を通るため、1 万 m² 未満の三角形がすべて除外される。
周南 51310655 で 16.4 m²、51310636 で 1 棟が実際に落ちていた。原因も対処も本設計と独立している。

**既存データの是正。** 本設計は新規取り込みにのみ効く。既存の 1,489 万棟は再取り込みまで変わらない。

## 未解決

**本番データとの対応が未実測である。**
本番 137 都市は上流由来で、変換器のバージョンは v3 系という以上に特定できていない。
本番の relation が複数の建物 ID を束ねているかは、再取り込み後に `ref_mlit_plateau` で確認する。

**変換器がマルチポリゴンで建物 ID を落とす件を上流に伝えていない。**
上流に #150 が OPEN だが内容が異なる可能性がある。別途確認する。

**穴のある建物の割合は 1 都市 10 メッシュの実測である。** 0.11%。都市による差は測っていない。

## 検証

取り込み後に次を確認する。

- DB の建物数が、変換出力の「建物 ID を持つ way」＋「`building` タグ付き multipolygon」の数と一致する（三角形の不具合を直した後）
- 「建物の中に建物」が 0 件になる
- 内側リングを持つ建物が DB に存在する（`ST_NumInteriorRings > 0`）
- API の応答で、穴のある建物が `type=multipolygon` として返る
- `parent_building_id` が新規取り込み分で NULL である
