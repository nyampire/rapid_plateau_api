# 合成 OSM id の採番と `plateau_id` の規約 設計

- 日付: 2026-08-04
- 関連: #39、#44、`feature/importer-source-fidelity`（取り込みを元データに忠実にする）

## 背景

API は DB の建物 1 行から OSM XML の要素を組み立てるとき、負の id を合成している。
族ごとに定数 offset を引く方式で、族の帯が建物 id の範囲と重なると衝突する。

`feature/importer-source-fidelity` で、穴のある建物を `type=multipolygon` として返すようになり、
族が 2 つ増えた（中庭の relation、内側リングの way）。
既存の `RELATION_ID_OFFSET = -1_000_000` はこのブランチ以前からある欠陥で、
`plateau_buildings.id` が本番で約 1,490 万に達しているため、すでに帯を越えている。

同じブランチで、`plateau_id` に relation の id が入るようになった。
これまで way の id しか入っていなかった欄で、OSM は way と relation の id 空間を分けているため、
値だけでは元の要素を特定できない。

どちらも、1,489 万行の再取り込みを跨ぐと後から変えにくくなる。

## 実測した事実

**衝突するのは同じ型どうしだけ。**
Rapid は entityID を型の頭文字付きで作る（`PlateauService.js:675`、`:858`）。
OSM の id も型ごとに独立しているので、way と relation の間では衝突しない。

既存コードのコメントは内側リング way について 3 条件を挙げているが、
そのうち relation を相手にする 2 つは型が違うので無害で、残るのは通常 way との 1 つだけ。
かわりにコメントが挙げていない条件が 1 つある。
`type=building` relation と `type=multipolygon` relation の衝突で、
`建物id_C == 建物id_A + 2,000,000` のときに起きる。
建物 id が約 1,490 万まであり offset の差が 200 万なので、候補の組は 1,290 万通りある。
旧データと新データは都市単位で混在するため、市境をまたげば同じセッションに載る。

**衝突の結果は重複ではなく消失。**
`PlateauService.js:859` が、すでに見た entityID の要素を捨てる。
`cache.seen` をクリアするのは `resetAsync()` だけで、タイルごとには消えない。
つまり衝突した建物は編集画面から黙って消える。
条件も「同じ bbox に両方が入る」ではなく「同じセッションでどちらも一度読まれる」まで広い。

**建物 id は減らない。**
`plateau_buildings.id` は SERIAL で、DELETE してもシーケンスは戻らない。
再取り込みは都市ごとに DELETE してから INSERT するので、全都市を 1 周するたびに
最大 id が約 1,490 万ずつ増える。固定 offset の帯はいつか必ず踏み越える。

**内側リングの本数は最大 4 本。**
変換済み 12 メッシュの `building` タグ付き `type=multipolygon` 18 件で数えた。
1 本が 16 件、3 本が 1 件、4 本が 1 件。

## 採番

型ごとに、建物 id と役割から一意に決める。

```
way      : -(建物id × 1000 + 環番号)   環番号 0 = 通常/外側、1..999 = 内側リング
relation : -(建物id × 10   + 種別)     種別 1 = type=building、2 = type=multipolygon
```

既存の 3 定数（`RELATION_ID_OFFSET`、`MULTIPOLYGON_RELATION_ID_OFFSET`、
`INNER_RING_WAY_ID_OFFSET`）は廃止し、乗数と種別コードに置き換える。

`type=building` relation が参照する outline メンバーと part メンバーの way id も、
同じ規則で導く。

### なぜ単射か

way: `建物id_A × 1000 + 環番号_A == 建物id_B × 1000 + 環番号_B` のとき、
環番号が 1000 未満なら商と余りが一意に決まるので、両辺の建物 id と環番号が一致する。

relation: 種別は `{1, 2}` の 2 値で 10 未満なので、同じ論法が前提なしに成立する。

**前提は「環番号 < 1000」の一つだけ。**
環番号が 1000 に達すると `(建物id+1) × 1000 + 0` と衝突する。
つまり建物 N の 1000 本目の穴が、建物 N+1 の通常 way の id を奪う。
奪われた側は編集画面から黙って消えるので、この前提は API 側で守る（「検知」の節）。

id が `(建物id, 役割)` の純粋な関数なので、この単射性はセッションを跨ぐ場合もそのまま成立する。
同じ建物はいつも同じ id をもらい、違う建物は必ず違う id をもらう。
サーバから観測できない `cache.seen` の蓄積を別途考える必要がなくなる。

### 桁数

最大値は 1,490 万 × 1000 で約 150 億。
JavaScript の安全整数 9×10¹⁵ の約 60 万分の 1 で、
全都市の再取り込み 1 周あたり 1,490 万の増加なら約 60 万周分の余裕がある。

## 検知

前提が一つなので、守る場所も一つで足りる。

境界を数え違えないよう、環番号で言う。
外側リングが環番号 0、内側リングが 1 から順に付く。
許されるのは**環番号 999 まで**、つまり内側リングは 1 棟あたり 999 本までである。

### この上限は API の制約であって、データの制約ではない

`geometry(Polygon,4326)` は内側リングの本数を制限しないし、ノード表も何本でも持てる。
制約があるのは API が OSM の id を組み立てる式だけである。

したがって**取り込み側では何も捨てない**。
捨てると、DB が問題なく保持できるデータを入口で失うことになり、
復旧に再変換と再取り込みが要る。
上限に触れるのは API の出力だけにとどめ、式を直せば次のリクエストから元に戻る状態を保つ。

環番号を振り直しても直らない点に注意する。
衝突の原因は割り当てた建物 id ではなく内側リングの本数なので、
変換や取り込みをやり直しても同じ結果になる。

| 場所 | 内容 |
|---|---|
| 事前確認 | 変換直後に、inner が 999 本を超える multipolygon を数える。取り込む前に人が判断する |
| 取り込み | 何も捨てない。内側リングが何本あってもそのまま保存する |
| API | 環番号が 1000 に達する建物は、そのレスポンスから外して `logger.warning` を出す。建物 id と内側リングの本数を出し、DB を引いて特定できるようにする |
| API | レスポンス内で同じ型の同じ id が二度出たら警告する |
| テスト | 内側リング 999 本が出力され、1000 本でそのレスポンスから外れることを固定する |

最悪の症状は「その建物が一時的に編集画面に出ない」で、復旧は式の修正だけで済む。
再取り込みも再変換も要らない。

API 側の一意性検査には、いま書かれるだけで読まれていない `emitted_db_ids` を使う。
式の証明が将来の変更で壊れたときの網になる。

## `plateau_id`

`w-30` / `r-30` の形にする。

`source_dataset` に `plateau_{都市コード}_{ファイル名}` が入っているので元ファイルは復元できる。
足りないのは型だけで、それを補うと変換出力のどの要素から来たかが一意に決まる。

この列は変換をやり直すと値が変わるので、**安定した識別子ではない**。
その役割は #30 で入れた `ref_mlit_plateau`（CityGML の建物 ID）が担う。
`plateau_id` は変換の記録に徹する。

読み手はコード上に存在しない（この repo にもダッシュボードにも SELECT が無い）。
それでも規約を決めるのは、障害調査で読まれるとしたら型が判らないと使えないためと、
再取り込みを跨ぐと DB が二つの規約に割れるため。

## 移行

スキーマ変更は無い。

既存の 1,489 万行に対しても、API が返す way id が `-建物id` から `-(建物id×1000)` に変わる。
この id は編集セッション内でしか生きないので永続化の問題は無い。
Rapid は id から DB id を逆算していないため、クライアント側の変更も要らない
（`PlateauService.js` は `osmEntity.id.fromOSM` で型の頭文字を付けるだけ）。

`plateau_id` の形式は、再取り込み済みの都市と未実施の都市で混在する。
読み手がいない列なので許容する。

## 対象外

**建物 id の詰め直し。**
`plateau_building_nodes.building_id` を全行書き換える必要があり、
ノード行は 1 億行規模なので 960MB の VPS では現実的でない。
安く済むのは全都市を一度に再取り込みするときだけで、
両テーブルを TRUNCATE して `ALTER SEQUENCE plateau_buildings_id_seq RESTART WITH 1` すればよい。
本設計の採番では id 空間が枯渇資源でなくなるので、詰め直す動機は id の確保ではなく
DB サイズの削減という別の目的になる。

**`osm_id` 列の扱い。** 一時 id が入っており読み手が無い点は `plateau_id` と似ているが、
本設計では触らない。

## 検証

- 各族の id が式どおりであること
- 内側リング 1000 本の建物が取り込みでは捨てられず、DB に保存されること
- 内側リング 999 本の建物が API から出力され、1000 本ではそのレスポンスから外れて警告が出ること
- 同じレスポンスに同じ型の同じ id が二度出ないこと
- `plateau_id` が way 由来で `w-`、relation 由来で `r-` で始まること
- 既存のテストで `-建物id` を期待している箇所が新しい式に更新されていること
