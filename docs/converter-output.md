# 変換出力の性質と、取り込みで対処できる範囲

PLATEAU の CityGML は [citygml-osm](https://github.com/yuuhayashi/citygml-osm) で `.osm` に変換され、
`plateau_importer2postgis.py` がそれを DB に取り込む。

この文書は**変換出力にどういう性質があり、取り込み側でどこまで対処できるか**をまとめる。
取り込みの規則を変えるとき、再取り込みの結果を確認するとき、変換器の挙動を疑ったときに読む。

個別タスクの設計は `docs/superpowers/specs/` にある。この文書はそれらをまたぐ恒久的な参照である。

---

## 先に知っておくこと: 融合

**変換器は、外壁の線分を共有する建物どうしを 1 つにまとめる。**
`RelationMarge.checkParts` が接触を判定し、`matomeru` が取り込む側の way を `building:part` に降格させる。
javadoc に明記された意図的な設計で、v2.3.1 から変わっていない。

この融合が、以下のほとんどの性質の原因である。融合の結果、出力にはこう現れる。

- 複数の実在建物をまたぐ**合成外形**の way が新しく作られる
- 元の建物の way は `building` から `building:part` にキーが変わる
- 両者を束ねる `type=building` の relation が作られる

**元データに `bldg:BuildingPart` は存在しない。**
変換器のソースに `BuildingPart` も `consistsOf` も 1 箇所も現れず、パーサが読むのは
`bldg:Building` と `lod0FootPrint` / `lod1Solid` / `lod2Solid` だけである。
**出力の `building:part` はすべて融合の産物であり、真の部分立体ではない。**

融合を止めると上流のテストが 8 件落ちる。relation が作られることを Issue 由来のテストが期待している。
**設計変更であって不具合修正ではない**ので、こちらから止めることはしない。

## 一覧

| 変換出力の性質 | 取り込みでの扱い |
|---|---|
| 合成外形の way が作られる | **対処済み** — 建物 ID を持たない建物 way は取り込まない |
| 実在建物が `building:part` に降格する | **対処済み** — 建物 ID があれば `building` として保存する |
| 建物の型が `building:part` の値側に移る | **対処済み** — `building` が無ければ `building:part` の値を型として読む |
| 中庭のある建物が `building:part` の multipolygon になる | **対処済み** — multipolygon は `building` / `building:part` のどちらでも建物とみなす |
| `type=building` の relation が実在しない親子を作る | **対処済み** — この relation は読まない |
| multipolygon の識別子が `gml:id` に置き換わる | **保存はできる** — 形式が混ざることを承知で保存する |
| **`outer` を持たない multipolygon が出る** | **直せない** — 保存する外形が存在しない |
| **合成外形にしか無いタグがある** | **ほぼ影響なし** — 実測で大半は他の要素にも同じ値がある |
| **余分な合成 part ができる (上流 #151)** | **未対処** — 判別する手立てが無い |
| **Lod1Solid 由来の巨大 part が独立して出る** | **API 出口で対処中** — #33 で判定条件を定めている |
| **同じ建物を way と multipolygon の 2 つで出す** | **未対処** — 統合すれば直せる。40 件中 27 件 |

以下、「直せない」「未対処」のものを詳しく書く。

## `outer` を持たない multipolygon

### 現象

`type=multipolygon` の relation で、メンバーが `inner` だけで `outer` が無いものが出る。
穴だけがあって外形が無い状態なので、ポリゴンを組み立てられない。

### 実測 (周南市、名前を持つ 81 メッシュ、建物 66,319 棟)

multipolygon 161 個のうち **4 個**。うち 2 個は `name` を持つ。

県立周南総合支援学校の例では、`inner` が 4 本あり、合計面積は同じ場所の合成外形の約 1/10 だった。
4 本とも閉じた妥当なリングで、それ自体は壊れていない。

### なぜ取り込み側で直せないか

外形として使える形が出力に存在しない。

候補になるのは融合外形だけだが、**融合外形は複数の建物にまたがる**ので、
それを 1 棟の外形として保存すると「実在しない建物を保存しない」という取り込みの原則に反する。
`inner` から外形を推定する方法も無い。穴の位置は外形の形を決めない。

### 取り込みの挙動

WARNING を出してスキップする。

```
⚠️ multipolygon relation -114664 をスキップ: outer member が 0 個 (期待値 1)
```

再取り込みのあと、このログの件数を数えれば影響範囲が判る。

### 影響

その建物が DB に入らない。名前を持つ場合は名前も失われる。
実測では 276 棟の名前つき建物のうち 1 棟がこれに該当した。

**上流に未報告。**原因の確定まで保留 (「報告の進め方」参照)。

### 原因 (2026-08-06 特定、citygml-osm 3.0.6 素のビルドで確認)

`CityModelParser` の `gml:exterior` の処理にある。

```java
else {
    // Issue #137: 同じ位置の solid way が既にある外形は捨てる
    this.osm.removeWay(elementWay);
    this.elementWay = null;          // ← ここで null になる
}
...
if ((multipolygon != null) && (elementWay != null)) {
    ...
    this.multipolygon.addMember(outer, "outer");   // ← 通らない
}
```

外形が Issue #137 の重複判定で捨てられると `elementWay` が null になり、
**multipolygon に `outer` が付かない**。`gml:interior` 側は後から `inner` を足すので、
穴だけを持つ multipolygon が残る。

計測で確認した事実 (周南市 51311567、1 メッシュ):

- `EXTERIOR DROPPED` は 182 回起きる。**そのうち出力に outer 無しで残るのは 1 件だけ**
- 残り 181 件は後段で `outer` を付け直されるか、`BuildingGarbage` に回収される
- 問題の relation は `outer` を**付けられたことも外されたこともない** (計測で両方 0 件)。
  `addMember` の `way == null` による黙った取りこぼしでもない (0 件)

**最初は `OutlineFactory` の inner 追加ループが原因だと読んだが、そこに guard を入れても
出力は 1 バイトも変わらなかった。**読みだけで決めず、計測して原因に行き着いた。

### 直せる見込み

**ある。**原因が 1 箇所に特定でき、素のビルドで再現・計測できている。
考えられる直し方は 2 つ。

1. 外形を捨てるとき、同じ位置にある既存の way を `outer` に使う
   (`existSamePositionWay` は真偽しか返さないので、該当 way を取れるようにする必要がある)
2. 外形を捨てた multipolygon は組み立てをやめる

どちらも上流のテストを壊さないかの確認が要る。ベースラインは 110 件中 4 件失敗
(コードではなく、テストが参照する gml がリポジトリに無いことによる)。

## 合成外形にしか無いタグ

### 現象

融合すると、元の建物が持っていた `name` などのタグが合成外形の側にも現れる。
合成外形は建物 ID を持たないので取り込まれない。
そのタグが合成外形にしか無ければ、DB に入らない。

### 実測 (同上、81 メッシュ)

取り込まない way 2,673 本のうち、DB の保存対象になるキーを持つのは 2,627 本。
ただしその内訳のほとんどは `height` `ele` `building:levels` で、**合成形状の値なので捨てるのが正しい**。

建物の同一性を表すタグ (`name` / `addr:*` / `amenity` / `shop` / `tourism` / `leisure` / `landuse`) を
持つのは **117 本**だけで、そのうち **109 本は同じ値を取り込む要素も持っている**。

残る 8 本 (名前 6 種) は、上の「`outer` を持たない multipolygon」と、
かつて降格 multipolygon を落としていた不具合の合算だった。後者は解消済みである。

### 結論

**この経路の情報損失は小さい。**
合成外形を捨てる規則そのものを見直す必要は無い。

## Lod1Solid 由来の巨大 part

CityGML の `lod1Solid` (建物全体の押し出し) が、独立した `building:part` として出力されることがある。
outline とほぼ同じ位置・形状・高さ・階数を持つので、`type=building` の relation の中で
outline と巨大 part が並ぶ形になる。

OSM の [Simple 3D buildings](https://wiki.openstreetmap.org/wiki/Simple_3D_buildings) は
立体どうしが共通面を持って重なることを避けるとしているので、この形は慣習に沿わない。

DB 全体 (12.66M outline) の調査では約 18 万 outline (1.4%) が該当する。
判定条件と対処は [#33](https://github.com/nyampire/rapid_plateau_api/issues/33) にある。
outline との重心距離とハウスドルフ距離が小さいことが決め手で、
これで本物の wing (別位置の棟) と分離できる。

上流 #149 の修正 (`lod1Solid` があるとき `lod2Solid` と `bldg:boundedBy` を無視する) は
このパターンには効かない。ローカルの jar で再現を確認している。
**上流に未報告。**原因の確定まで保留 (「報告の進め方」参照)。

## 余分な合成 part (上流 #151)

作者は v3.0.6 で解決と回答しているが、報告者が挙げた周南市の 4 建物
(`35215-bldg-38144` / `38145` / `38147` / `38184`) で再現する。
part が 7 個 (実在 4 + 合成 3) 出力され、報告内容と一致した。

合成 part は建物 ID を持たないため、現在の取り込み規則では自動的に落ちる。
つまり**実害は出ていない**。ただし「建物 ID を持たない = 合成」という前提に寄りかかっている。

**この事実は上流に未報告。**原因の確定まで保留 (「報告の進め方」参照)。
報告するなら「解決済みとされた挙動が再現する」という事実報告の形になる。

## 識別子の形式が要素の型で変わる

### 実測 (同上、81 メッシュ)

| 要素 | `ref:MLIT_PLATEAU` の中身 | 件数 |
|---|---|---|
| way | 建物 ID (`35215-bldg-N`) | 66,215 |
| way | 無し (合成外形) | 2,673 |
| multipolygon | **`gml:id` (`bldg_<uuid>`)** | 129 |
| multipolygon | 無し | 32 |

**multipolygon には建物 ID が 1 つも付かない。**
元データ側は欠かしていない (周南市・毛呂山町の実測でいずれも欠落 0) ので、変換の過程で置き換わっている。

この挙動は上流 [#150](https://github.com/yuuhayashi/citygml-osm/issues/150) に挙がっている。
同じ周南市 51310655 のメッシュが例として使われており、v3 で中空部分を multipolygon に変換する
ようにした結果だと作者が説明している。**こちらから報告することは無い。**

### 影響

DB の `plateau_buildings.ref_mlit_plateau` 列に **2 系統の識別子が混ざる**。

どちらも一意なので、同一都市内の重複検査は成立する。
ただし `<citycode>-bldg-<n>` という形式を前提に parse すると、multipolygon 由来の行で壊れる。

2026-08-06 時点で、この列の形式を解釈しているコードは本リポジトリにも dashboard にも無い。
列は不透明な文字列として保存・読み出しされている。**新しくこの列を読むときは 2 系統あることを前提にする。**

## 本番データとの対応

本番の 137 都市は上流由来で、**変換に使われたバージョンは特定できていない**。
元の `.osm` が残っていないため、事後に確定する手立ても無い。

そのため、この文書の実測値は**自前変換 (citygml-osm 3.0.6) の出力についての値**である。
本番データが同じ比率で同じ性質を持つとは限らない。

コホート比較では、上流データも同種の不整合を同オーダーで持つ (1.67% 対 自前 3.0.6 で 1.15%)。
**再取り込みを済ませれば、この不確かさ自体が消える。**

## 変換器側で直したほうがよいこと

取り込みで回避できるものも含めて、**本来どちらで直すのが素直か**を整理する。
手元で変換器に手を入れるときの出発点にする。

| 現象 | 取り込みでの回避 | 変換器で直すと |
|---|---|---|
| `outer` を持たない multipolygon が出る | **回避できない**。保存する外形が無い | 唯一の解。**原因は特定済み** (Issue #137 の重複判定で `elementWay` が null になる) |
| 同じ建物を way と multipolygon の 2 つで出す | 統合できる (下記) | 統合の仕組みごと不要になる |
| multipolygon に建物 ID でなく `gml:id` が付く | twin がある 27/40 でのみ回復できる。**残り 13 は回復できない** | 識別子が 1 系統になり、`ref_mlit_plateau` の 2 系統問題も消える |
| 中庭のある建物が `building:part` に降格する | 値を型として読めば回避できる | タグの意味が素直になる。上流 #146 / #147 と同じ領域 |
| 余分な合成 part (#151) | 建物 ID が無いので自動的に落ちる | 「建物 ID が無い = 合成」という前提に頼らなくてよくなる |
| Lod1Solid 由来の巨大 part | API 出口で filter する (#33) | filter が不要になる |

### 二重出力の詳細

穴のある建物が、**穴を潰した way** と **穴のある multipolygon** の 2 つで出力される。
周南市 81 メッシュの実測では、降格した multipolygon 40 件のうち **27 件**に相手の way がある。

| | 形 | 識別子 |
|---|---|---|
| way | 穴が潰れている | **建物 ID** |
| multipolygon | 穴がある | `gml:id` |

**片方ずつしか持っていない。**どちらを捨てても何かを失う。

27 件すべてで、元データの `gml:id` → `uro:buildingID` が相手の way の `ref:MLIT_PLATEAU` と一致した。
タグ (`name` / `height` / `ele` / `building:levels` / `start_date`) の食い違いは 0 件で、
相手が 2 つ見つかる曖昧さも 0 件だった。
`building` タグ付きの multipolygon 117 件には相手の way が 1 つも無く、**降格したものに限られる**。

取り込み側では、外側リングが一致することを条件に 2 つを 1 棟に統合できる
(ジオメトリは multipolygon、識別子は way から取る)。
ただし**変換器が 1 棟を 1 要素で出せば、この統合そのものが要らなくなる。**

## 変換器を直すときに壊してはいけない性質

取り込みは変換出力の次の性質に依存している。変換器に手を入れるときは、ここを崩さないこと。

1. **合成外形は建物 ID を持たない。**
   取り込みは「建物 ID を持たない建物 way は合成物」として捨てている。
   合成外形に識別子が付くようになると、実在しない建物が DB に入る。
   上流 #149 が `newOutline.removeTag` を削除しているので、**バージョンによっては既に崩れうる**。
   再取り込みのたびに同一都市内の `ref_mlit_plateau` 重複を確認するのはこのため。

2. **実在建物は建物 ID を持つ。**
   元データ側は欠かしていない (実測で欠落 0)。
   変換の過程で落とすと、その建物は取り込まれない。

3. **`building:part` の値は元の建物の型である。**
   12 の型すべてで、元データの用途コードが `building` 側と一致することを確認済み。
   降格のときに値を `yes` に潰すと、型が失われる。

4. **multipolygon の `outer` はちょうど 1 本。**
   0 本だと保存できない (上記)。2 本以上は取り込みが警告を出してスキップする。

## 上流 Issue との対応 (2026-08-06 時点)

上流リポジトリは [yuuhayashi/citygml-osm](https://github.com/yuuhayashi/citygml-osm)。
**報告する前にこの表を確認する。**同じことが既に挙がっていることがある。

| この文書で扱っていること | 上流 Issue | 状態 |
|---|---|---|
| multipolygon の識別子が `gml:id` になる | [#150](https://github.com/yuuhayashi/citygml-osm/issues/150) OPEN | **既出。**例が周南市 51310655 で本文書の実測と同じデータ。v3 で multipolygon 変換を入れた結果と作者が説明済み |
| `building` / `building:part` のキーが不安定 | [#146](https://github.com/yuuhayashi/citygml-osm/issues/146) / [#147](https://github.com/yuuhayashi/citygml-osm/issues/147) OPEN | 症状は既出。ただし**向きが逆**で、上流は「`building:part` であるべき way が `building` になっている」を報告している |
| 余分な合成 part | [#151](https://github.com/yuuhayashi/citygml-osm/issues/151) CLOSED | 「v3.0.6 で解決」とあるが**再現する**。未報告 |
| `outer` を持たない multipolygon | 該当なし | 未報告 |
| 同じ建物の way と multipolygon の二重出力 | 該当なし | 未報告 |
| Lod1Solid 由来の巨大 part | 該当なし | 未報告 |

### 報告の進め方 (2026-08-06 決定)

**未報告のものは、手元で変換器を直して原因を確定できるまで報告を保留する。**

現象の記述だけを持ち込むと、原因の切り分けを上流にお願いすることになる。
こちらは元データも変換環境も揃っていて、`citygml-osm` をビルドして走らせる手順も確立している。
原因と修正案まで揃えてから出すほうが、受け取る側の手数が少ない。

保留を解く条件は次の 3 つを満たすこと。

1. 手元の `citygml-osm` で現象を再現できる
2. 原因の箇所をソース上で特定できる
3. 修正を当てて現象が消え、**上流のテストが落ちないこと**を確認できる

3 が満たせない場合 (既存のテストが期待を固定している場合) は、不具合報告ではなく
設計の相談になる。そのときは形を変えて出すか、出さないかを改めて判断する。

### 報告しないと決めたもの

**融合の設計そのもの。** 接する独立建物を 1 つの relation にまとめる挙動は javadoc に明記された
意図的な設計で、上流のテスト 8 件がそれを固定している。
不具合報告ではなく設計変更の提案になるため、こちらからは持ち込まない。
取り込み側で選別する形で完結させている。

## 再取り込みのあとに確認すること

1. `outer` 無し multipolygon の WARNING の件数
2. **同一都市内の `ref_mlit_plateau` の重複** — 重複は合成形状の混入を意味する
   (バージョンによっては合成外形も識別子を持ちうる。上流 #149 が `newOutline.removeTag` を削除している)
3. 「建物の中に建物」が 0 件になること
4. 内側リングを持つ建物が存在すること (`ST_NumInteriorRings > 0`)
5. `parent_building_id` が新規取り込み分で NULL であること

## 測り直すときの手順

変換器の挙動を自分で確かめる手順は次のとおり。

```bash
cp <citygml-osm>/conversion.json <作業dir>/     # 無いと FileNotFoundException
cd <作業dir>                                    # .gml を置く
java -jar <citygml-osm>/target/citygml-osm-3.0.6-jar-with-dependencies.jar 1st
```

- **引数はモード名** (`1st` / `2nd` / `3rd` / `4th` / `pack` / `unpack`)。ファイル名ではない。
  ファイル名を渡すとどの分岐にも入らず、**何もせず exit 0** する
- `loadDir()` はカレントディレクトリの `.gml` を全部処理する
- Java 17 が要る (11 では class file version 61 で動かない)
- 1 メッシュあたり数十秒〜数分かかる

取り込み側の挙動は、DB 接続なしで `parse_osm_file_safe` を直接呼べば確かめられる
(`tests/conftest.py` の `bare_importer` fixture が同じことをしている)。
