# リレーションに入らない部分立体を独立した建物として出力する

対象の Issue: #42（親を持たない部分立体）、#39（親と重ならない部分立体）

## 目的

API が出力から外している実在の建物を、エディタの地図に表示します。
あわせて、リレーションに属さない `building:part` の way を出力しないようにします。
#39 の対処の案 C にあたり、取り込みを直す案 B が入るまでの処置です。

## 規則

リレーションの中に出力しない部分立体は、`building` として出力します。
ただし、独立した建物か1棟の建物の一部かを判別できない部分立体は、今の扱いを変えません。

| 部分立体 | 今の出力 | 変更後 |
|---|---|---|
| 親の外形と重なる | リレーションの `part` | 変えない |
| 親が記録されていない（#42） | 単独の `building:part` の way | `building` の way |
| 親の外形と重ならない（#39） | 出力しない | `building` の way |
| 親の外形と重ならず、同じリレーションの兄弟と建物ID を共有する | 出力しない | 変えない |
| 親の外形と重ならず、建物ID が文字列の `Null` | 出力しない | 変えない |

建物ID は `ref:MLIT_PLATEAU` の値です。

## 背景

2026-11-27 の本番のデータでの件数です。

- 親の外形と重ならない部分立体は 45,623 件で、親は 21,516 個です。
- 親が記録されていない部分立体は6件です（東大阪市4件、大阪市2件）。6件とも建物ID を持ちます。親を失った原因は確かめていません。
- 外形と重ならない部分立体ができるのは、citygml-osm が接する独立建物を1つのリレーションにまとめ、その全体を覆わない形で外形を作るためです。citygml-osm に同梱の試験データ `Issue28_50303525_op.osm` でも、3つのリレーションで、外形が部分立体を合わせた形の 11〜38% しか覆っていませんでした。
- 本番のデータは、取得元で変換済みのファイルを取り込んでいます。どの版の citygml-osm で変換したかは確かめられません。

外したままにする部分立体の件数は、次のとおりです。

- 兄弟と建物ID を共有するものは 1,398 件です（さいたま市 1,393 件、静岡市5件）。さいたま市では部分立体 17,351 件のうち 16,118 件が兄弟と建物ID を共有していて、1棟の建物の複数の形と考えられます。元の CityGML では確かめていません。
- 建物ID が `Null` のものは 1,777 件です。館林市、横須賀市、掛川市、名古屋市、高槻市、北九州市の6都市では、建物のほぼすべての建物ID が `Null` で、ID から独立建物かを判別できません。

独立した建物として出力するのは、45,623 − 1,398 − 1,777 = 42,448 件と、親が記録されていない6件です。

## 前提

API は、取得範囲の中にある外形を先に選び、その外形を親に持つ部分立体を取り出しています（`related_parts`）。
部分立体そのものの位置では取り出していません。
外形から離れた部分立体（最大 838m）を独立した建物として出すには、部分立体を自分の位置で取り出す必要があります。
今のままだと、同じ建物が地図に出るかどうかが、外形が取得範囲に入っているかで決まります。

## 対処の案

| 案 | 内容 | トレードオフ |
|---|---|---|
| A | #45 の処置を外し、離れた部分立体もリレーションのまま出力する | 変更は小さい。外形と重ならない建物を1棟の一部として OSM に入れることになる |
| B | 取り込みで、外形と重ならない部分立体をリレーションから外し、独立した建物として保存する | データは正しくなる。全都市の取り込み直しが要る |
| C | API の出口で、リレーションに入らない部分立体を `building` として出力する | 取り込み直しを待たずに表示できる。B のあとは不要になる |

利用者が C を選びました。

C の中での取り出し方には、2つの方法があります。

- 要求のたびに、取得範囲の中の部分立体について、親の外形と重なるかを問い合わせで判定する。DB に手を入れずに済む。応答の時間が延びるおそれがある。
- 取り込みのときに判定の結果を列に保存しておく。応答は速い。DB の変更と全都市の書き込みが要り、B とほぼ同じ手間になる。

前者を採ります（私の判断）。
C は B までの処置なので、DB の構造を変えないほうを選びました。

## 変更する箇所

`osmfj_plateau_api.py` の `get_buildings_in_bbox` の問い合わせ

- 取得範囲の中にあり、親の外形と重ならず、外したままにする条件に当たらない部分立体を取り出す CTE を足す。
- その CTE には、`orphan_parts` と同じ重複の除去（`dedup_key`）と行政界のフィルタを当てる。
- 同じ行が `related_parts` と新しい CTE の両方から返っても、出力は1回だけにする。

`buildings_to_osm_xml`

- 独立した建物として出す行は、`building` のタグで単独の way にし、どのリレーションにも入れない。
- 親が記録されていない部分立体も同じ扱いにする。
- `intersects_parent is False` の行を外す処理は残す。`related_parts` が返した外形と重ならない行は、ここで外れる。独立した建物として出す行は、新しい CTE から返った行のほうを使う。
- `dropped_far_parts` のログは、外したままにする条件に当たった件数だけを数えるように変える。今のままだと、新しい CTE で出し直す行まで数えてしまう。
- 独立した建物として出した件数もログに出す。
- `dropped_far_parts` の撤去条件のコメントを、今の規則に合わせて書き直す。

`plateau_height_warning.py`

- 独立した建物として出す行は、部分立体としてではなく建物として判定する。
- つまり `part-over-outline` を判定せず、`needle` を判定の対象にする。

Rapid は変えません。
独立した建物は、ほかの建物と同じく way ごとに既存の建物との重なりで隠され、高さの転記元にもなります。

## 試験

`tests/test_drop_far_parts_endpoint.py` と `tests/test_intersects_parent_flag.py` の期待を、新しい規則に合わせて直します。
新しく固定する場合は、次の5つです。

- 親が記録されていない部分立体が `building` の way になる。
- 外形と重ならない部分立体が、外形が取得範囲の外にあっても、自分の位置で `building` の way として出る。
- 外形と部分立体の両方が取得範囲に入るとき、その部分立体の way が1本だけ出る。
- 兄弟と建物ID を共有するもの、建物ID が `Null` のものは出ない。
- 独立した建物として出した行が、`needle` の判定を受け、`part-over-outline` の判定を受けない。

## 残る問題

外していた 45,623 件のうち 142 件は、ほかの建物の行と、自分の面積の5% を超えて重なります。
外したままにする 37 件を除いた 105 件は、出力すると JOSM の重なりの警告になるおそれがあります。
内訳は、同じリレーションの ID の違う部分立体の中に入るもの 83 件、ほかのリレーションの外形の中に入るもの 11 件、写しの疑いがあるもの3件、独立した建物と一部が重なるもの7件、2種類の相手と重なるもの1件です。
この 105 件は今回の規則では区別せず、出力します（私の判断）。
全体の 0.25% で、外しておくための条件を足すと、B が入るまでの処置としては重くなるためです。

行政界での削除でも部分立体が欠けている可能性があります。
取り込みの最後に、重心が市の外にある建物を消す処理があるためです。
親子の外部キーは連鎖削除なので、合成の外形の重心が市の外にあると、市の中にある部分立体も一緒に消えます。
消えた行は DB に残らないので、件数は数えていません。
今回の変更では戻らないので、B の側で扱います。

## 範囲外

- 取り込みの変更（案 B）
- 部分立体のほうが親より大きい 8,432 件
- Rapid で承認したあとにリレーションが失われる件（#39 の最初の報告）
- 親を失った6件の原因の調査

## 実装に任せること

- 新しい CTE の名前と、重なりの判定の書き方
- 応答の時間の確認の方法。本番と同じ規模のデータで、変更の前後の時間を比べる。
