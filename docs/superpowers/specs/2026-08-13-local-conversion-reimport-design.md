# 手元で変換してサーバへ送る取り込みの設計

- 日付: 2026-08-13
- 関連: [#21](https://github.com/nyampire/rapid_plateau_api/issues/21)（上流取得をローカル変換へ切り替え）の Phase 1 と Phase 2、[PR #53](https://github.com/nyampire/rapid_plateau_api/pull/53)（取得の道具）、[PR #54](https://github.com/nyampire/rapid_plateau_api/pull/54)（新規構築の DDL）

## 背景

サーバを新しく契約して一から組み直す。新しい DB は空で、148 都市を順に取り込む。

上流の配信元は止まっているため、CityGML は G空間情報センターから取得し、citygml-osm で変換する。
変換器は Java で 4GB のヒープを使うので、960MB のサーバには載らない。**変換は手元で行う。**

いまサーバにある 3 本のスクリプトは、138 都市を完走させた実績を持つ。
どのリポジトリにも入っていないので、そのままではサーバを捨てたときに失われる。

## 実測した事実

**取り込みはファイル 10 個ごとに commit する** (`BATCH_SIZE = 10`)。
都市 1 件が丸ごと巻き戻るわけではなく、途中で落ちればそこまでの分が残る。

**取り込みは開始前にその都市の既存データを自分で消す。**
`--citycode` が渡っていれば、`plateau_buildings` と `plateau_building_nodes` から該当都市の行を削除してから始める。
そのため `plateau_purge.py` を別に呼ぶ必要はなく、再実行も安全である。
削除は独立して commit されるので、**途中で落ちた都市は行が 0 件のこともある**。

**行政界フィルタは外部キーの CASCADE に依存している。**
`DELETE FROM plateau_buildings` の 1 文だけを実行し、ノード側の削除を任せている。
CASCADE が無い DB では、市境の外に落ちる建物を持つ最初の都市で失敗する。PR #54 で DDL を直した。

**対応エリアのビューは誰も作らない。**
`plateau_coverage.py --init` でしか作られず、`refresh` は無ければ `view_not_found` を返して終わる。

**手元に全都市の CityGML は置けない。**
展開後は全国で 168GB、手元の空きは 36GB しかない。1 都市ずつ処理して消す。最大は浜松市の 4.4GB。

**転送量は全国で 12GB** (`.osm`)。取得は Range 抽出で 8.84GB。

## 全体の流れ

2 つの段に分け、時間的にも分ける。並行させない。

### 第 1 段（手元、5〜6 時間）

都市ごとに繰り返す。

```
CKAN から建物 gml を取り出す → citygml-osm で変換 → .osm をサーバへ送る → 手元を消す
```

手元に同時に置くのは 1 都市ぶんだけ。
送り終えた都市を `shipped.txt` に追記し、再開はこれを見て飛ばす。

### 引き渡し

送り終えたら、`ship_all.sh` が `shipped.txt` の都市コードをサーバの `reimport_targets.txt` として置く。
この一覧が「取り込んでよい」という合図を兼ねる。転送中の都市がバッチに拾われることはない。

送り先は都市ごとのディレクトリで、`<転送先>/<citycode>/*.osm` の形にする。
`reimport_one.sh` はこのディレクトリを `--data-dir` に渡す。

### 第 2 段（サーバ、十数時間）

既存の `reimport_batch.sh` がそのまま走る。

```
targets.txt を読む → 都市ごとに reimport_one.sh → done.txt に追記
```

サーバは最大 12GB の `.osm` を抱え、取り込んだ都市から順に解放する。

## 対象は 148 都市

現行 DB の全都市が対象になる。取得計画 (`ckan_download_plan.csv`) は 147 都市ぶんしかない。
宇城市 43213 が、2026-08-11 に再取り込み済みだったため作成時に除かれている。

新サーバは空なので**宇城市を計画に戻す**。`build_download_plan.py` に 43213 を渡して再生成する。

## ファイルの置き場所

サーバに置く 3 本もリポジトリに入れる。ダッシュボードの `deploy/` と同じ形にする。

```
scripts/reimport/          手元で走らせる
  httpzip.py               PR #53
  build_download_plan.py   PR #53
  scan_bldg.py             PR #53
  extract_city.py          PR #53
  ship_city.sh             新規: 1 都市を取り出し・変換・転送・掃除
  ship_all.sh              新規: 一覧を回す。再開つき
  ship.env.example         新規: java と jar と転送先の設定

deploy/                    サーバに置く
  reimport_one.sh          縮めたもの (取り込み + 掃除)
  reimport_batch.sh        いまのまま
  reimport_watchdog.sh     パスを引数にする (下記)
  README.md                置き方と運用手順
```

### `ship_city.sh`

都市コードを 1 つ受け取り、順に行う。

1. `extract_city.py` で `udx/bldg/*.gml` を取り出す
2. 取り出した `.gml` の数が `extract_city.py` の報告する `meshes` と一致することを確かめる
3. `conversion.json` を作業ディレクトリへ置き、`java -jar <jar> 1st` を実行する
4. `.osm` の数が `.gml` の数と一致し、**各ファイルが空でなく `</osm>` で終わっている**ことを確かめる
5. `rsync` で転送する
6. 転送先のファイル数が手元と一致することを確かめる
7. 手元の作業ディレクトリを消し、`shipped.txt` に `<citycode> <osm数>` を追記する

2 を入れるのは、`extract_city.py` が zip 内のパスを basename に潰して書き出すため。
同じ basename のメンバーが 2 つあると黙って上書きされ、ファイル数だけが減る。

4 でファイルの中身まで見るのは、数の一致では切り詰めを検出できないため。
JVM が途中で落ちると、書きかけの `.osm` も 1 個として数えられる。

どこかで失敗したら `shipped.txt` に記録せず終了し、**作業ディレクトリは消さない**。

### `ship_all.sh`

都市一覧を読み、`shipped.txt` にあるものを飛ばして `ship_city.sh` を呼ぶ。
ディスクの空きが閾値を割ったら止める。

全都市を試したあと、成功した都市の一覧をサーバの `reimport_targets.txt` として置く。
失敗した都市があっても置く。**1 都市の失敗で第 2 段を止めない。**
失敗した都市は一覧に出し、`ship_all.sh` を再実行すればその都市だけをやり直せる。
第 2 段のあとで追加の取り込みを流す。

### `reimport_one.sh`

4 段から 2 段に縮む。

```
取り込む (--no-zip --citycode) → 成功したときだけ .osm を消す
```

ダウンロードは手元へ移り、purge は取り込みが内包しているので消える。

**入力の削除は成功時だけにする。**
現行は `trap cleanup EXIT` で、失敗しても watchdog に kill されても消える。
以前の入力は再ダウンロードできたので無害だったが、今後は取り出し・変換・転送をやり直すことになる。

**開始前に入力を確かめる。** ディレクトリが存在し `.osm` を 1 つ以上含むこと。
満たさなければ専用の終了コードで落ちる。取り込み側は `mkdir(exist_ok=True)` を `parents` 無しで呼ぶので、
ディレクトリが無いとコンストラクタで例外になり、生のトレースバックが出る。

`--citycode` は明示して渡す。推定に頼らない。
推定が外れて "unknown" になると、既存データの削除と行政界フィルタの両方が飛ばされる。

ディスクの事前確認とログの形は残す。ただし閾値は下記のとおり測り直す。

### `reimport_watchdog.sh`

**「変更しない」は成り立たない。**
実行中のプロセスが本物の wrapper かどうかを、`case` 文でコマンドラインの前方一致を見て判定している。
比較する文字列に `reimport_one.sh` の絶対パスが直接書き込まれているため、置き場所を変えると一致しなくなる。

パスが変わると `is_real_wrapper` が常に false になり、90 分の打ち切りも `kill` も黙って効かなくなる。
ログだけは正常に出続けるので気づけない。

**判定に使うパスを環境変数にする。** 変更はこの 1 箇所に留める。
再開、pause、apt の時間帯回避、ディスクとメモリの監視という中身には触らない。

### `reimport_batch.sh`

変更しない。

## 段の境目で完了と言える条件

| 境目 | 完了の条件 | 満たさないとき |
|---|---|---|
| 取り出し | `.gml` の数が `extract_city.py` の報告と一致 | 記録せず終了。作業ディレクトリを残す |
| 変換 | `.osm` の数が `.gml` と一致し、各ファイルが `</osm>` で終わる | 同上 |
| 転送 | 転送先のファイル数が手元と一致 | 同上 |
| 取り込みの開始 | 入力ディレクトリに `.osm` が 1 つ以上ある | 専用の終了コードで落ちる |

サーバ側の失敗は既存のとおり。
`reimport_one.sh` が 0 以外で終われば `failed.txt` に記録してバッチは次へ進み、
ディスク不足 (exit 2) のときだけ全体を止める。

## 進捗の記録と復旧

手元の `shipped.txt` とサーバの `done.txt` があり、片方が消えると食い違う。

**当初は DB のメッシュ数で復旧する案だったが、成立しない。**
`source_dataset` はその `.osm` から建物が 1 件でも入ったときにしか値を持たない。
行政界フィルタ、極小三角形の除去、メッシュをまたぐ重複の除去、元データに建物が無いメッシュ、
いずれの場合もそのメッシュは DB に現れない。完了した都市が未完了に見える。

代わりに `shipped.txt` に `<citycode> <osm数>` を記録し、これを正とする。
サーバ側にも同じ内容が `reimport_targets.txt` として渡るので、片方が消えても他方から作り直せる。

DB は「行があるか」だけを見る補助に使う。行が 0 件なら確実に未完了である
（取り込みは開始時に削除を commit するため）。行があっても完了とは限らない。
判断に迷う都市は再実行する。取り込みが開始時に消すので重複は起きない。

## 並列変換は入れない

手元は 8 コアあるので変換を並列にすれば速くなるが、第 1 版では入れない。

一度きりの作業に 5〜6 時間かかるのは許容できる。
並列にすると同時に展開する CityGML が増えてディスクを圧迫し (浜松市 1 都市で 4.4GB)、失敗時のログも混ざる。

遅すぎると判ってから足す。

## 新サーバで測り直すもの

古い数値をそのまま持ち込まない。どちらも実機が要る。

**1 都市あたりの上限時間** (`MAX_CITY_MIN=90`)。
138 都市を回したときの値だが、新しい年度のデータはメッシュが増えている
(福島市 59→212、安曇野市 94→212、全国 17,726→18,352)。
ダウンロードが無くなるぶんは短くなるが、3 倍に増えた都市で足りるかは別である。
検証でメッシュの多い都市を 1 件測ってから決める。

**ディスクの閾値** (`THRESHOLD_KB=5GB`、watchdog の halt が 3GB)。
これまでの最大の一時領域は 1 都市ぶんだったが、今後は 12GB の `.osm` が最初から載り、
取り込みが進むほど DB が育つ (144 都市で約 36GB)。空きが最小になるのは開始直後である。
新サーバの容量を決めてから、12GB + DB + WAL と一時領域を足して逆算する。

## `DEPLOY.md` を新規構築と更新の 2 部に分ける

実際に人が辿るのはこの文書である。いまは新規構築しか扱っていないが、**参照されるのは更新のときのほうが多い。**

### 新規構築側に足りないもの

- 取り込みの節が止まった配信元 (`plateau_downloader.py`) を前提にしている
- `--no-zip` に触れていない
- `plateau_coverage.py --init` が無い。ビューが無いままでは Rapid の対応エリア表示が出ない
- `scp` するファイルの一覧に `plateau_coverage.py` と `plateau_purge.py` が無い
- ディスクの見積もりと、対応エリアの再計算に要る一時 swap の手順が無い
- `dash_city_master` を第 2 段の前に用意する順序が書かれていない (下記)

### 更新側は章ごと無い

いまの「8. 運用」はログの見方、都市の追加、サービスの起動停止だけである。
更新の手順が無く、代わりに**事故を起こす記述が 1 行残っている**。

**Rapid の配信物を消してはいけないものごと消す。**

```bash
rsync -avz --delete dist/ user@vps:/var/www/rapid/
```

ダッシュボードは web root の中にあり `dist/` には含まれないので、この行はダッシュボードを全削除する。
新規構築の時点ではまだ存在しないため実害が出ないが、**同じ行が更新のたびに使われる**。
`--exclude '/dashboard/'` を付け、送信前にドライランで削除対象が 0 件であることを確かめる手順にする。

更新側に書くもの。

| 場面 | 要点 |
|---|---|
| API のコード更新 | `git pull` → 必要ならスキーマ移行 → 再起動。順序を守る理由も書く。起動中のプロセスは再起動まで古いコードを持つ |
| Rapid の更新 | `npm run build` → `npm run dist` → ドライラン → `--exclude '/dashboard/'` 付き rsync |
| 都市の追加・再取り込み | 本設計の経路。1 都市なら手元で `ship_city.sh`、サーバで `reimport_one.sh` |
| 対応エリアの再計算 | 都市を足したあとに 1 回。一時 swap を足して `--no-concurrent` |

`npm run build` と `npm run dist` の両方が要ることは明記する。
`dist/data/l10n/*.min.json` を作るのは `build` 側なので、`dist` だけを流すと
JS は新しいのに文言が古いまま配信される。2026-07-19 に実際に踏んでいる。

## `dash_city_master` は第 2 段の前に用意する

行政界フィルタはこの表を参照し、無ければ警告を出して素通りする。
`DEPLOY.md` は「ダッシュボードを併設しない構成では作らなくてよい」と書いており、それ自体は正しい。

ただし**このフィルタは取り込み時にしか働かず、後から掛け直す経路が無い**。
用意せずに 148 都市を流すと、市境をまたぐ重複を抱えたまま全都市が入り、直すには再取り込みしかない。

第 2 段を始める前に、ダッシュボードを立てて `dash_city_master` を `boundary_geom` 付きで用意する。
順序として `DEPLOY.md` に書く。

## 検証

段階を踏む。

1. 最小の都市 1 件 (青ケ島村 13402、8 メッシュ) で `ship_city.sh` を通し、転送先のファイル数を確かめる
2. 手元の PostgreSQL に対して縮めた `reimport_one.sh` を走らせ、行数とメッシュ数を確かめる
3. メッシュの多い都市 1 件 (福島市 07201、59→212) で所要時間を測り、上限時間を決める
4. `ship_all.sh` を 3 都市の一覧で走らせ、2 都市目で止めてから再実行し、3 都市目から続くことを確かめる
5. 新サーバで 148 都市の一覧を流す

2 には条件がある。現行の `reimport_one.sh` は `df --output=avail` を使っており、これは GNU coreutils の書式で macOS では動かない。
パスと `df` の呼び方を環境変数か OS 判定で吸収する。吸収しないなら、この検証は Linux 上で行う。

**自動テストは 3 つ足す。** いずれもシェルの分岐で、実行時には気づきにくいもの。

- 取り込みが失敗したとき、入力ディレクトリを消さないこと
- ディスク不足のとき、終了コードが 2 であること (バッチ全体を止める合図)
- 入力ディレクトリが無いとき、専用の終了コードで落ちること

引数の綴りが合っているかは自動テストにしない。取り込み側が `argparse` なので、最初の 1 都市で必ず落ちる。

## 全部終わったあとの確認

1. 148 都市すべてに行があること
2. 都市ごとのメッシュ数が `shipped.txt` に記録した数と一致すること (差がある都市は内訳を確認する)
3. `ref_mlit_plateau` が NULL の行が 0 件であること
4. 行政界フィルタが実際に働いたこと。市境をまたぐ都市を数件抜き取り、取り込みログの除外件数が 0 でないこと
5. 「建物の中に建物」を数都市で抜き取り確認
6. 対応エリアを `--init` してから `--refresh` する。一時 swap を足して 1 回だけ

6 は都市ごとに走らせない。960MB のメモリで OOM を起こす。

## 運用メモに残すこと

watchdog が pause を立てるとき、`SIGTERM` を送るのは `reimport_one.sh` だけで、
その下の `python3` には届かない。取り込みは走り続け、10 ファイルごとの commit も続く。

再実行時に取り込みが既存データを消すので最終的な整合は取れるが、
同じ都市に 2 つの取り込みが同時に走る状態は起こりうる。
pause のあとは `plateau_importer2postgis.py` が残っていないか確かめてから再開する。

## 採らなかった案

**DB を進捗の正にする。**
`done.txt` を廃し、行の有無で判定する。状態が 1 箇所になるが、バッチの心臓部を書き換えることになる。
実績のある部分に触るので検証をやり直す必要があり、行の有無が完了を意味しないため判定も単純にならない。

**手元から SSH で全部駆動する。**
サーバ側のスクリプトを持たず、手元の 1 本が転送も取り込みも指示する。
Mac を全工程で拘束し、watchdog も失われる。

**送るたびに取り込む。**
サーバの `.osm` が 1 都市ぶんで済むが、Mac を十数時間から日単位で拘束する。
既存の再開・pause・監視も使えない。
