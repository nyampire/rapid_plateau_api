# 手元で変換してサーバへ送る取り込みの設計

- 日付: 2026-08-13
- 関連: [#21](https://github.com/nyampire/rapid_plateau_api/issues/21)（上流取得をローカル変換へ切り替え）の Phase 1 と Phase 2、[PR #53](https://github.com/nyampire/rapid_plateau_api/pull/53)（取得の道具）、[PR #54](https://github.com/nyampire/rapid_plateau_api/pull/54)（新規構築の DDL）

## 背景

サーバを新しく契約して一から組み直す。新しい DB は空で、148 都市を順に取り込む。

上流の配信元は止まっているため、CityGML は G空間情報センターから取得し、citygml-osm で変換する。
変換器は Java で 4GB のヒープを使うので、960MB のサーバには載らない。**変換は手元で行う。**

いまサーバにある 3 本のスクリプトは、138 都市を完走させた実績を持つ。
どのリポジトリにも入っていないので、そのままではサーバを捨てたときに失われる。

## 実測した事実

**取り込みはファイル 10 個ごとに commit する** (`BATCH_SIZE = 10`)。
都市 1 件が丸ごと巻き戻るわけではなく、途中で落ちればそこまでの分が残る。

**取り込みは開始前にその都市の既存データを自分で消す。**
`--citycode` が渡っていれば、`plateau_buildings` と `plateau_building_nodes` から該当都市の行を削除してから始める。
そのため `plateau_purge.py` を別に呼ぶ必要はなく、再実行も安全である。
削除は独立して commit されるので、**途中で落ちた都市は行が 0 件のこともある**。

**行政界フィルタは外部キーの CASCADE に依存している。**
`DELETE FROM plateau_buildings` の 1 文だけを実行し、ノード側の削除を任せている。
CASCADE が無い DB では、市境の外に落ちる建物を持つ最初の都市で失敗する。PR #54 で DDL を直した。

**対応エリアのビューは誰も作らない。**
`plateau_coverage.py --init` でしか作られず、`refresh` は無ければ `view_not_found` を返して終わる。

**手元に全都市の CityGML は置けない。**
展開後は全国で 168GB、手元の空きは 36GB しかない。1 都市ずつ処理して消す。最大は浜松市の 4.4GB。

**転送量は全国で 12GB** (`.osm`)。取得は Range 抽出で 8.84GB。

## 全体の流れ

2 つの段に分け、時間的にも分ける。並行させない。

### 第 1 段（手元、5〜6 時間）

都市ごとに繰り返す。

```
CKAN から建物 gml を取り出す → citygml-osm で変換 → .osm をサーバへ送る → 手元を消す
```

手元に同時に置くのは 1 都市ぶんだけ。
送り終えた都市を `shipped.txt` に追記し、再開はこれを見て飛ばす。

### 引き渡し

送り終えたら、`ship_all.sh` が `shipped.txt` の都市コードをサーバの `reimport_targets_<日時>.txt` として置く。
この一覧が「取り込んでよい」という合図を兼ねる。転送中の都市がバッチに拾われることはない。

**一覧は毎回新しい名前で置き、既存のものを上書きしない。**
失敗した都市を第 2 段の走行中に送り直すことがあり、そのとき固定名だと走行中のバッチが読むファイルを書き換える。
`reimport_batch.sh` が一覧を起動時に 1 回読むのか都市ごとに読み直すのかで挙動が変わり、どちらであるかは現物を見ないと判らない。
名前を分ければ、どちらでも安全になる。

送り先は都市ごとのディレクトリで、`<転送先>/<citycode>/*.osm` の形にする。
`reimport_one.sh` はこのディレクトリを `--data-dir` に渡す。

同じディレクトリに `manifest.txt` を置き、`.osm` の枚数を書く。
`shipped.txt` はこの時点では手元にしか無いので、失うと枚数を知る手立てがなくなる。
DB から数え直すこともできない（後述）。
枚数をサーバ側にも置けば、`shipped.txt` を失っても転送先から作り直せる。

### 第 2 段（サーバ、十数時間）

既存の `reimport_batch.sh` がそのまま走る。

```
targets.txt を読む → 都市ごとに reimport_one.sh → done.txt に追記
```

サーバは最大 12GB の `.osm` を抱え、取り込んだ都市から順に解放する。

## 対象は 148 都市

現行 DB の全都市が対象になる。取得計画 (`ckan_download_plan.csv`) は 147 都市ぶんしかない。
宇城市 43213 が、2026-08-11 に再取り込み済みだったため作成時に除かれている。

新サーバは空なので**宇城市を計画に戻す**。`build_download_plan.py` に 43213 を渡す。
既存の 147 行は残り、43213 の行が足される。

当初この節は「渡して再生成する」と書いていた。
当時の `build_download_plan.py` は CSV を読まずに作り直していたので、
そのとおり実行すると 147 都市の計画が 1 行に潰れた。
追加になるよう直したうえで、この記述も合わせた。

## ファイルの置き場所

サーバに置く 3 本もリポジトリに入れる。ダッシュボードの `deploy/` と同じ形にする。

```
scripts/reimport/          手元で走らせる
  httpzip.py               PR #53
  build_download_plan.py   PR #53
  scan_bldg.py             PR #53
  extract_city.py          PR #53
  ship_city.sh             新規: 1 都市を取り出し・変換・転送・掃除
  ship_all.sh              新規: 一覧を回す。再開つき
  ship.env.example         新規: java と jar と転送先の設定

deploy/                    サーバに置く
  reimport_one.sh          縮めたもの (取り込み + 掃除)
  reimport_batch.sh        いまのまま
  reimport_watchdog.sh     パスを引数にする (下記)
  README.md                置き方と運用手順
```

### `ship_city.sh`

都市コードを 1 つ受け取り、順に行う。

1. `extract_city.py` で `udx/bldg/*.gml` を取り出す
2. 取り出した `.gml` の数が `extract_city.py` の報告する `meshes` と一致することを確かめる
3. `conversion.json` を作業ディレクトリへ置き、`java -jar <jar> 1st` を実行する
4. `.osm` の数が `.gml` の数と一致し、**各ファイルが空でなく `</osm>` で終わっている**ことを確かめる
5. `rsync` で転送する
6. 転送先のファイル数が手元と一致することを確かめる
7. 転送先に `manifest.txt` を置き、`.osm` の枚数を書く
8. 手元の作業ディレクトリを消し、`shipped.txt` に `<citycode> <osm数>` を追記する

2 は二重の網である。`extract_city.py` は zip 内のパスを basename に潰して書き出すので、
同じ basename のメンバーが 2 つあると黙って上書きされ、ファイル数だけが減る。
これは `extract_city.py` 自身が取り出す前に検出して落ちるようになったが、
下流でも数を照合しておく。

4 でファイルの中身まで見るのは、数の一致では切り詰めを検出できないため。
JVM が途中で落ちると、書きかけの `.osm` も 1 個として数えられる。

`.gml` の側は `extract_city.py` が一時ファイルに書いてから名前を付けるので、
切り詰められた `.gml` は残らない。同じ守り方を `.osm` にも入れたいが、
変換器の出力先はこちらで決められないので、4 の中身の確認で代える。

3 は java の終了コードを見る。`set -e` に任せず、明示的に確かめる。

どこかで失敗したら `shipped.txt` に記録せず終了し、**作業ディレクトリは検査用に別名へ退避する**。
消さないだけでは足りない。`extract_city.py` は `os.makedirs(dest, exist_ok=True)` を呼ぶだけで
既存の中身を掃除しないので、前回の失敗が残した `.gml` と `.osm` がそのまま残る。
年度が変わってメッシュ集合が縮んだ都市では、枚数の照合が何度やり直しても合わない状態に固定される。
再試行は必ず空のディレクトリから始める。

### `ship_all.sh`

都市一覧を読み、`shipped.txt` にあるものを飛ばして `ship_city.sh` を呼ぶ。
ディスクの空きが閾値を割ったら止める。

**一覧の出所は `ckan_download_plan.csv` である。**
開始時に件数が 148 であることを確かめ、違えば止める。
現物の CSV は 147 行で宇城市 43213 を含まないので、そのまま流すと 147 都市ぶんの
`reimport_targets` ができ、4 つの門も第 2 段も何も検出しない。
気づくのは 20 時間後の最終確認 1 になる。

全都市を試したあと、成功した都市の一覧をサーバの `reimport_targets_<日時>.txt` として置く。
失敗した都市があっても置く。**1 都市の失敗で第 2 段を止めない。**
失敗した都市は一覧に出し、`ship_all.sh` を再実行すればその都市だけをやり直せる。

再送分の取り込みは第 2 段の完了後に、別の一覧として流す。
第 2 段の走行中に送り直すこと自体は構わないが、そのとき新しい一覧を走行中のバッチに拾わせない。
一覧を毎回新しい名前で置くのはこのためである。

### `reimport_one.sh`

4 段から 2 段に縮む。

```
取り込む (--no-zip --citycode) → 成功したときだけ .osm を消す
```

ダウンロードは手元へ移り、purge は取り込みが内包しているので消える。

**入力の削除は成功時だけにする。**
現行は `trap cleanup EXIT` で、失敗しても watchdog に kill されても消える。
以前の入力は再ダウンロードできたので無害だったが、今後は取り出しから転送までをやり直すことになる。

**開始前に入力を確かめる。** ディレクトリが存在し、`.osm` の枚数が `manifest.txt` の数とちょうど一致すること。
満たさなければ専用の終了コードで落ちる。取り込み側は `mkdir(exist_ok=True)` を `parents` 無しで呼ぶので、
ディレクトリが無いとコンストラクタで例外になり、生のトレースバックが出る。

「1 つ以上」では足りない。枚数が欠けたまま取り込まれた都市は行を持ち、`ref_mlit_plateau` も入り、
行政界フィルタも働くので、4 つの門と最終確認をすべて通り抜ける。
`.osm` はサーバのディスクに何時間も置かれるので、欠ける機会はある。

ちょうど一致を求めることで、別の穴も同時に塞がる。
取り込み側の `_discover_osm_files` は `--no-zip` のとき `rglob("*.osm")` を使うので、
入力ディレクトリの下に無関係な `.osm` が紛れ込むと全部拾い、全部に同じ `--citycode` が付く。

`--citycode` は明示して渡す。推定に頼らない。
**現行は `--citycode` をまったく渡していない。**入力ディレクトリの名前が都市コードになっているので、
推定が偶然あたっているだけである。転送先の構造を変えるなら、この暗黙の前提は持ち込めない。

推定が外れて "unknown" になると、既存データの削除と行政界フィルタの両方が飛ばされる。
`city_code` は `NOT NULL` なので INSERT 自体は落ちるが、落ちるのは 1 都市ぶんの作業が終わったあとになる。

掃除の対象は入力ディレクトリを丸ごとにする。
現行も per-city のディレクトリごと消しているので形は変わらないが、置き場所が変わる。
取り込みは `--no-zip` でも `<data-dir>/extracted` を作るので (`plateau_importer2postgis.py:106-109`)、
`.osm` だけを消す書き方にすると空のディレクトリが 148 個残る。

ディスクの事前確認とログの形は残す。ただし閾値は下記のとおり測り直す。
現行の確認は `df --output=avail /` でルートの空きを見ており、閾値の既定は 5GB である。

### `reimport_watchdog.sh`

**「変更しない」は成り立たない。**
実行中のプロセスが本物の wrapper かどうかを、`case` 文でコマンドラインの前方一致を見て判定している。
比較する文字列に `reimport_one.sh` の絶対パスが直接書き込まれているため、置き場所を変えると一致しなくなる。

パスが変わると `is_real_wrapper` が常に false になり、90 分の打ち切りも `kill` も黙って効かなくなる。
ログだけは正常に出続けるので気づけない。

**判定に使うパスを環境変数にする。** 変更はこの 1 箇所に留める。
再開、pause、apt の時間帯回避、ディスクとメモリの監視という中身には触らない。

現物を読んで確かめた。判定は `case "$cmdline" in "bash <絶対パス>/reimport_one.sh "*)` の形で、
バッチ側が `bash ~/reimport_one.sh "$CITY"` と呼ぶので今は一致している。
置き場所を変えると一致しなくなる、という読みはそのとおりだった。

**`kill` はプロセスグループを対象にしていない。**wrapper の PID 1 つに `kill -TERM` を送るだけである。
その下の `python3` は生き残る。取り込みを 2 つ同時に走らせない、の節を参照。

pause を立てたあと watchdog 自身も `exit` する。
バッチも次の都市の手前で止まるので、再開には `reimport_pause` を消して両方を起動し直すことになる。
この手順を運用メモに書く。

失敗が続いたときの守りもある。
watchdog 起動後の直近 12 件に `FAIL exit=` が 3 件あると pause を立てて終わる。
148 都市の途中で系統的な問題が起きたときに、これが最初に効く。

### `reimport_batch.sh`

**「変更しない」は成り立たなかった。**一覧のパスが変数に固定されていて、引数を取らない。

一覧を毎回新しい名前で置くという方針は、このままでは実現できない。
バッチが読むのは固定名の 1 本だけである。

一覧のパスを第 1 引数で受け取り、既定を現在の固定名にする。変更はこの 1 箇所に留める。

読んで確かめた性質を 2 つ書き残す。どちらも設計が依存している。

**一覧はループの `done < "$LIST"` で 1 回開かれ、そのまま読み進む。**
別 inode に差し替えるぶんには走行中のループに影響しないが、同じファイルを truncate して
書き直すと読み位置がずれる。固定名のまま上書きするのは危険である。

**`done.txt` の照合は `grep -qx` で、行全体との一致を見る。**
記録されるのは都市コードだけで、`failed.txt` のほうは `<citycode> <終了コード>` の 2 列になる。
照合先は `done.txt` だけなので、失敗した都市は再実行で必ずやり直される。
設計が前提にしていたとおりだった。

一覧の各行は `tr -d '[:space:]'` で空白を除かれる。
`<citycode> <osm数>` のような 2 列を渡すと 2 つの数字が連結された文字列になるので、
一覧に書けるのは都市コードだけである。枚数を `manifest.txt` に置く判断はここでも要る。

## 段の境目で完了と言える条件

| 境目 | 完了の条件 | 満たさないとき |
|---|---|---|
| 取り出し | `.gml` の数が `extract_city.py` の報告と一致 | 記録せず終了。作業ディレクトリを残す |
| 変換 | `.osm` の数が `.gml` と一致し、各ファイルが `</osm>` で終わる | 同上 |
| 転送 | 転送先のファイル数が手元と一致 | 同上 |
| 取り込みの開始 | `.osm` の枚数が `manifest.txt` の数とちょうど一致 | 専用の終了コードで落ちる |
| 第 2 段の開始 | 148 都市すべてが `dash_city_master` に行を持ち `boundary_geom` が NULL でない。ノードの外部キーが `ON DELETE CASCADE` | SQL 1 本で確認してから始める |
| 第 2 段の 1 都市目 | `ref_mlit_plateau` が NULL の行が 0 件。行政界フィルタの除外件数を確認。建物の中に建物が無い | ここで止める |

変換の門には条件が 1 つ付く。
元データに建物が無いメッシュがあり、変換器がそのメッシュに `.osm` を出さない実装なら、
「`.osm` の数が `.gml` と一致」は正しい変換結果を失敗と判定する。
その都市は `shipped.txt` に載らず、何度やり直しても同じ結果になる。
変換器の挙動は検証 1 で確かめる。出さない実装なら、門を
「java の終了コードが 0」「出た `.osm` がすべて `</osm>` で終わる」「枚数を記録する」に組み替える。

**1 都市目の門を置くのは、判定を最終確認まで遅らせないためである。**
`ref_mlit_plateau` は `ref:MLIT_PLATEAU` タグから取るだけなので、jar が想定と違えば全都市が NULL になる。
148 都市を流し切ってから気づくと、20 時間がまるごと無駄になる。
最終確認には全都市への横展開だけを残す。

第 2 段の開始の門も、遅れると取り返せない類である。
行政界フィルタは取り込み時にしか働かず、後から掛け直す経路が無い。

この表より手前にも守りがある。
`extract_city.py` は basename の衝突を取り出す前に検出し、
書き出した大きさが zip の申告と違えば落ちる。
`httpzip.py` は Range 要求に 206 以外が返ったら落ちる。
配信元が Range を無視して全文を返すと、例外も出さずに別の場所のデータを読むため。

サーバ側の失敗は既存のとおり。
`reimport_one.sh` が 0 以外で終われば `failed.txt` に記録してバッチは次へ進み、
ディスク不足 (exit 2) のときだけ全体を止める。

## 進捗の記録と復旧

手元の `shipped.txt` とサーバの `done.txt` があり、片方が消えると食い違う。

**当初は DB のメッシュ数で復旧する案だったが、成立しない。**
`source_dataset` はその `.osm` から建物が 1 件でも入ったときにしか値を持たない。
行政界フィルタ、極小三角形の除去、メッシュをまたぐ重複の除去、元データに建物が無いメッシュ、
いずれの場合もそのメッシュは DB に現れない。完了した都市が未完了に見える。

代わりに `shipped.txt` に `<citycode> <osm数>` を記録し、これを正とする。

**枚数はサーバ側にも渡す。**転送先の `manifest.txt` に書く。
`reimport_targets` に載るのは都市コードだけなので、これだけでは `shipped.txt` を作り直せない。
`manifest.txt` があれば、転送先を走査して都市コードと枚数の両方を復元できる。
`reimport_targets` が第 1 段の完了時にしか生まれない以上、それまでは `shipped.txt` が唯一の記録になる。
`manifest.txt` は都市ごとに置かれるので、その期間も守られる。

DB は「行があるか」だけを見る補助に使う。行が 0 件なら未完了と見てよい。
取り込みは開始時に削除を commit するので、途中で落ちた都市は 0 件でありうる。
正常に完了して 0 件になる都市が無いことは前提であって、証明ではない。
148 都市はいずれも建物を持つので成り立つが、成り立たない都市を足すときはこの判定が使えなくなる。

行があっても完了とは限らない。
判断に迷う都市は再実行する。取り込みが開始時に消すので重複は起きない。

## 並列変換は入れない

手元は 8 コアあるので変換を並列にすれば速くなるが、第 1 版では入れない。

一度きりの作業に 5〜6 時間かかるのは許容できる。
並列にすると同時に展開する CityGML が増えてディスクを圧迫し (浜松市 1 都市で 4.4GB)、失敗時のログも混ざる。

遅すぎると判ってから足す。

**ただし転送を測っていない。**
`ship_city.sh` は変換のあとに rsync を直列で行うので、転送は変換と重ならない。
全国 12GB は上り 100Mbps なら 16 分だが、10Mbps なら 2.7 時間かかる。
すさみ町の実測から逆算した変換の総時間は 2.2 時間程度なので、上りが遅ければ転送が支配項になる。

上り帯域を測ってから、都市 N の転送と都市 N+1 の変換を重ねるかを決める。
これは並列変換と違ってヒープも作業ディスクも増えないので、却下した案とは費用が違う。

## 新サーバで測り直すもの

古い数値をそのまま持ち込まない。どちらも実機が要る。

**1 都市あたりの上限時間** (`MAX_CITY_MIN=90`)。
138 都市を回したときの値だが、新しい年度のデータはメッシュが増えている
(福島市 59→212、安曇野市 94→212、全国 17,726→18,352)。
ダウンロードが無くなるぶんは短くなるが、3 倍に増えた都市で足りるかは別である。

**測る対象はメッシュが増えた都市ではなく、大きい都市である。**
行政界フィルタはバッチごとに呼ばれるが、判定する範囲はそのバッチではなく都市全体になる
(`plateau_importer2postgis.py:1270` から `:1296`)。
`NOT ST_Contains` は否定なので索引が効かず、その都市の残存行すべてに点内包判定が走る。
所要はメッシュ数に対して二乗で伸びる。

横浜市 14100 は 868K 建物あり、計画にも載っている。浜松市 22130 は 1,048 メッシュある。
福島市 07201 は「最も増えた」都市であって「最も大きい」都市ではないので、
そこで測った値から `MAX_CITY_MIN` を決めると、大都市で打ち切りが起きる。
検証の対象を横浜市と浜松市に変える。

**取り込みのピークメモリ**。
`node_coordinate_map` と `processed_geometry_hashes` は `__init__` でしか初期化されず
(`plateau_importer2postgis.py:116-117`)、都市 1 件のあいだ累積し続ける。
バッチ境界の `del` が解放するのはバッチ内の変数だけで、`BATCH_SIZE` はこの 2 つを抑えない。
横浜市なら座標キーは数百万件になる。
postgres が OOM で落ちた実績のあるサーバなので、時間と一緒にピーク RSS も取る。

**ディスクの閾値** (`THRESHOLD_KB=5GB`、watchdog の halt が 3GB)。
これまでの最大の一時領域は 1 都市ぶんだったが、今後は 12GB の `.osm` が最初から載り、
取り込みが進むほど DB が育つ (144 都市で約 36GB)。

空きが最小になるのは**終了直前**である。
開始時は `.osm` 12GB と DB 0GB、終了時は `.osm` 0GB と DB 36GB で、使用量は単調に増える。
向きを取り違えて開始時の 12GB を基準に閾値を決めると、
13 時間走ったあとの 140 都市目で `exit 2` が出てバッチ全体が止まる。
新サーバの容量を決めてから、終了時点の 36GB + WAL と一時領域を足して逆算する。

## `DEPLOY.md` を新規構築と更新の 2 部に分ける

実際に人が辿るのはこの文書である。いまは新規構築しか扱っていないが、**参照されるのは更新のときのほうが多い。**

### 新規構築側に足りないもの

- 取り込みの節が止まった配信元 (`plateau_downloader.py`) を前提にしている
- `--no-zip` に触れていない
- `plateau_coverage.py --init` が無い。ビューが無いままでは Rapid の対応エリア表示が出ない
- `scp` するファイルの一覧が 3 ファイルだけで、`plateau_coverage.py` と `plateau_purge.py` が無い。`deploy/` 一式も足す
- ディスクの見積もりと、対応エリアの再計算に要る一時 swap の手順が無い
- `dash_city_master` を第 2 段の前に用意する順序が書かれていない (下記)
- Rapid の配信物を作る節が `npm run dist` しか書いていない。更新側と同じく `build` と両方が要る

### 更新側は章ごと無い

いまの「8. 運用」はログの見方、都市の追加、サービスの起動停止だけである。
更新の手順が無く、代わりに**事故を起こす記述が 1 行残っている**。

**Rapid の配信物を消してはいけないものごと消す。**

```bash
rsync -avz --delete dist/ user@vps:/var/www/rapid/
```

ダッシュボードは web root の中にあり `dist/` には含まれないので、この行はダッシュボードを全削除する。
新規構築の時点ではまだ存在しないため実害が出ないが、**同じ行が更新のたびに使われる**。
`--exclude '/dashboard/'` を付け、送信前にドライランで削除対象が 0 件であることを確かめる手順にする。

更新側に書くもの。

| 場面 | 要点 |
|---|---|
| API のコード更新 | `git pull` → 必要ならスキーマ移行 → 再起動。順序を守る理由も書く。起動中のプロセスは再起動まで古いコードを持つ |
| Rapid の更新 | `npm run build` → `npm run dist` → ドライラン → `--exclude '/dashboard/'` 付き rsync |
| 都市を足す、取り込み直す | 本設計の経路。1 都市なら手元で `ship_city.sh`、サーバで `reimport_one.sh` |
| 対応エリアの再計算 | 都市を足したあとに 1 回。一時 swap を足して `--no-concurrent` |

`npm run build` と `npm run dist` の両方が要ることは明記する。
`dist/data/l10n/*.min.json` を作るのは `build` 側なので、`dist` だけを流すと
JS は新しいのに文言が古いまま配信される。2026-07-19 に実際に踏んでいる。

## `dash_city_master` は第 2 段の前に用意する

行政界フィルタはこの表を参照し、無ければ警告を出して素通りする。
`DEPLOY.md` は「ダッシュボードを併設しない構成では作らなくてよい」と書いており、それ自体は正しい。

ただし**このフィルタは取り込み時にしか働かず、後から掛け直す経路が無い**。
用意せずに 148 都市を流すと、市境をまたぐ重複を抱えたまま全都市が入り、直すには再取り込みしかない。

第 2 段を始める前に、ダッシュボードを立てて `dash_city_master` を `boundary_geom` 付きで用意する。
順序として `DEPLOY.md` に書く。

**表があるだけでは足りない。**判定の SQL は `JOIN` と `boundary_geom IS NOT NULL` の両方を条件にするので
(`plateau_importer2postgis.py:1296-1301`)、行が無い都市と `boundary_geom` が NULL の都市は素通りする。
そのときのログは「削除対象なし (境界未登録 or 全件境界内)」で、
フィルタが働いて 0 件だった場合と区別がつかない。
一部の都市だけ登録が漏れている状態は、抜き取りの確認では見つからない。

第 2 段の開始前に SQL 1 本で全 148 都市を確かめる。
同じ場所で `plateau_building_nodes.building_id` の `ON DELETE CASCADE` も確認する。
検証 2 は手元の PostgreSQL に対して行うので `dash_city_master` が無く、
フィルタも CASCADE も一度も動かないまま第 2 段に入ることになる。

## 検証

段階を踏む。

1. 最小の都市 1 件 (青ケ島村 13402、8 メッシュ) で `ship_city.sh` を通し、転送先のファイル数と `manifest.txt` を確かめる。
   あわせて、建物が無いメッシュに対して変換器が `.osm` を出すかを見る
2. 手元の PostgreSQL に対して縮めた `reimport_one.sh` を走らせ、行数とメッシュ数を確かめる
3. 大きい都市 1 件 (横浜市 14100、868K 建物) で所要時間とピーク RSS を測り、上限時間を決める。
   浜松市 22130 (1,048 メッシュ) でも測る
4. `ship_all.sh` を 3 都市の一覧で走らせ、2 都市目で止めてから再実行し、3 都市目から続くことを確かめる
5. 第 2 段を都市の途中で落として再開し、その都市がやり直されることを確かめる
6. 新サーバで 148 都市の一覧を流す

2 には条件がある。現行の `reimport_one.sh` は `df --output=avail` を使っており、これは GNU coreutils の書式で macOS では動かない。
パスと `df` の呼び方を環境変数か OS 判定で吸収する。吸収しないなら、この検証は Linux 上で行う。

**自動テストは 3 つ足す。** いずれもシェルの分岐で、実行時には気づきにくいもの。

- 取り込みが失敗したとき、入力ディレクトリを消さないこと
- ディスク不足のとき、終了コードが 2 であること (バッチ全体を止める合図)
- 入力ディレクトリが無いとき、専用の終了コードで落ちること

引数の綴りが合っているかは自動テストにしない。取り込み側が `argparse` なので、最初の 1 都市で必ず落ちる。

## 全部終わったあとの確認

1. 148 都市すべてに行があること
2. 都市ごとのメッシュ数が `shipped.txt` に記録した数と一致すること (差がある都市は内訳を確認する)
3. `ref_mlit_plateau` が NULL の行が 0 件であること (1 都市目の門を全都市へ広げる)
4. 行政界フィルタが実際に働いたこと。市境をまたぐ都市を数件抜き取り、取り込みログの除外件数が 0 でないこと
5. 「建物の中に建物」を数都市で抜き取り確認
6. 対応エリアを `plateau_coverage.py --init` で作る。一時 swap を足して 1 回だけ

6 は `--init` だけでよい。`--init` はビューを作ったあと `refresh(concurrent=False)` まで実行する
(`plateau_coverage.py:313-316`)。

**続けて `--refresh` を叩いてはいけない。**
`--init` でビューが populated になるので、次の `--refresh` は `--no-concurrent` を付けない限り
CONCURRENTLY を選ぶ (`:320`)。960MB で避けたいと言っている当の経路である。
やり直すときは `--refresh --no-concurrent` を使う。

6 は都市ごとに走らせない。960MB のメモリで OOM を起こす。

## 取り込みを 2 つ同時に走らせない

watchdog が pause を立てるとき、`SIGTERM` を送るのは `reimport_one.sh` だけで、
その下の `python3` には届かない。取り込みは走り続け、10 ファイルごとの commit も続く。

**「再実行すれば整合が取れる」は成り立たない。**当初この節はそう書いていたが、誤りだった。

`building_id_counter` は `SELECT MAX(osm_id) FROM plateau_buildings WHERE osm_id > 0` から取る
(`plateau_importer2postgis.py:267`、`:298`)。都市で絞っていないので全体の最大値である。
この値がそのまま新しい行の `osm_id` になる (`:974`)。

2 つ目の取り込みが後から起動すると、生き残っている 1 つ目が commit 済みの最大値を読むので、
以後の採番範囲が丸ごと重なる。
`osm_id` に一意制約は無い。

引き当ては `SELECT osm_id, id FROM plateau_buildings WHERE osm_id = ANY(%s)` で
(`:1236`)、こちらも `city_code` で絞っていない。
続く `dict()` が重複キーを最後の行で潰す (`:1239`)。
結果として都市 B のノードが都市 A の建物行にぶら下がる。
あとで都市 A を取り込み直すと、CASCADE で都市 B のノードが消える。

例外は出ず、行数も 0 にならないので、4 つの門と最終確認をすべて通り抜ける。

しかもこれは pause だけの話ではない。
90 分の打ち切りが wrapper を kill した場合、バッチは次の都市へ進むので、
同時に走るのは別々の都市になる。無人で十数時間走るあいだに起こりうる。

現物を読んで確かめた。watchdog は wrapper の PID 1 つに `kill -TERM` を送るだけで、
プロセスグループを対象にしていない。読みは当たっていた。

**対策は wrapper 側に置く。**`reimport_one.sh` が終了するときに、自分が起動した
`python3` を確実に落とす。子の PID を控えておき、`trap` で `kill` する。

watchdog 側でグループごと落とす案は採らない。
`pgrep` で拾った PID からグループを消しに行くことになり、watchdog の kill の範囲が広がる。
そこは実績のある部分で、pause の判定や失敗の数え方と同じスクリプトに入っている。

加えて `reimport_batch.sh` が都市を開始する前に、`plateau_importer2postgis.py` が
残っていないことを確かめる。一覧のパスを引数化するのと同じ 1 回の変更に含める。

## サーバの 3 本に入れる変更

現物を読んで確かめた結果、変更は 3 本すべてに入る。
当初は `reimport_batch.sh` を変更しない想定だったが、成り立たなかった。

| スクリプト | 変更 |
|---|---|
| `reimport_one.sh` | 4 段から 2 段に縮める。入力の削除を成功時だけにする。`--citycode` を明示する。開始前に `manifest.txt` と枚数を照合する。終了時に子の `python3` を落とす |
| `reimport_batch.sh` | 一覧のパスを第 1 引数で受け取る。都市を始める前に取り込みの残存を確かめる |
| `reimport_watchdog.sh` | wrapper の判定に使うパスを環境変数にする |

いずれも 1 箇所ずつに留める。
再開、pause、apt の時間帯回避、失敗の数え方、ディスクとメモリの監視には触らない。

第 2 段の開始前に `done.txt` と `failed.txt` が空であることを確かめる。
どちらも過去の実行のぶんが残るので、空でないまま始めると都市が飛ばされる。

## 採らなかった案

**DB を進捗の正にする。**
`done.txt` を廃し、行の有無で判定する。状態が 1 箇所になるが、バッチの心臓部を書き換えることになる。
実績のある部分に触るので検証をやり直す必要があり、行の有無が完了を意味しないため判定も単純にならない。

**手元から SSH で全部駆動する。**
サーバ側のスクリプトを持たず、手元の 1 本が転送も取り込みも指示する。
Mac を全工程で拘束し、watchdog も失われる。

**送るたびに取り込む。**
サーバの `.osm` が 1 都市ぶんで済むが、Mac を十数時間から日単位で拘束する。
既存の再開、pause、監視も使えない。

## この設計の外に出したもの

どちらも `plateau_importer2postgis.py` の変更になる。
138 都市を完走させた部分なので、別に切って検証を分ける。

**行政界フィルタを最終バッチだけに寄せる。**
いまはバッチごとに都市全体を判定するので、所要がメッシュ数の二乗で伸びる。
大都市で `MAX_CITY_MIN` を超えるなら要る。
超えるかどうかは検証 3 の実測で決まるので、その結果を待つ。

**都市 1 件のあいだ累積する 2 つの dict を、バッチ境界で解放する。**
`node_coordinate_map` は座標の重複除去に使うので、単純に消すと同じ座標が別ノードになる。
消してよいかは重複除去の要件を確かめてからになる。
こちらも検証 3 のピーク RSS 次第である。
