# 面積の条件で type=building リレーションを選んで取り込む

- 日付: 2026-08-28
- 前提: [2026-08-26 の設計](2026-08-26-walless-building-roof-design.md)（無壁舎を `building=roof` にする）
- 前提: コミット `4cd2b96`（2026-08-04、リレーションを読むのをやめた変更）

## 背景

変換出力の `type=building` リレーションについて、次の 5 つの類型が区別されずに作られている、という指摘があった。

| 類型 | 中身 |
|---|---|
| a | 1 つの建物の中で、部分ごとに階数や屋根の形が異なる |
| b | 大きめの建物の入り口などに庇が付いている |
| c | 工場や学校で、複数の棟を隣接させたり渡り廊下でつないだりしている |
| d | 戸建ての住宅とカーポート |
| e | 住宅密集地の、複数の戸建て |

[2026-08-26 の設計](2026-08-26-walless-building-roof-design.md)では、この件は対象にならないと結論した。
`4cd2b96` で取り込み器がリレーションを読まなくなっており、d も e も既に分解済みだったためである。

その後、c はリレーションとして配信したい、という判断が出た。
本設計はそれを実現する。

## いま何が起きているか

`4cd2b96` の前後で挙動が変わっている。
変わったのはコードではなくデータである。

| | 旧サーバ | 新サーバ |
|---|---|---|
| 取り込み器の版 | `4cd2b96` 以降 | `4cd2b96` 以降 |
| データを作った版 | `4cd2b96` より前 | `4cd2b96` 以降 |
| `parent_building_id` を持つ行 | 1,632,072 件 | 0 件 |
| リレーションを持つ都市 | 143 | 0 |
| 配信されるリレーションの集合 | 665,464 | 0 |

新サーバに切り替えた時点で、665,464 集合のリレーションが配信から消える。
本設計を入れないかぎり、c も含めて全部消える。

## 決めたこと

最大の部材の面積が 300 平方メートル以上のリレーションだけを取り込む。

条件はこの 1 つだけである。
建物区分も用途も高さも部材の数も使わない。

合成外形はそのまま `outline` として取り込む。
2026-08-04 より前と同じ扱いに戻す。

配信でメンバーの建物の型を落とすのをやめる。

## なぜ面積 1 つで足りるか

d と e は、部材がどれも小さい。
戸建ての建築面積は PLATEAU の実測で中央値 67 平方メートル、上位 10% でも 174 平方メートルである。
カーポートと庇はさらに小さい。

最大の部材が 300 平方メートル以上の集合には、戸建てだけの組み合わせは入りにくい。

この条件は建物区分に依存しない。
建物区分は都市によって入っていないことがある（実測で 3 都市中 1 都市が 0%）。
面積は図形から計算できるので、どの都市でも同じ規則が使える。

`buildingRoofEdgeArea` の属性も都市によって欠けるが、これも使わない。
`.osm` の座標から計算する。

## なぜ 2 番目の部材にも条件を置かないか

一度「2 番目が 200 平方メートル以上」という条件を検討し、外した。

この条件が落としていたのは d ではなく b だった。
実測では、最大 615 に対して 2 番目が 11、最大 672 に対して 30、という形が落ちていた。
大きい建物に庇が 1 つ付いた形である。

b は指摘の中で「a に含まれる」「別々でも許容されうる」とされており、分解すべき側ではない。
d は主たる建物が戸建てなので、最大の条件だけで落ちる。

条件を足すと b を巻き添えにするだけで、d には効かない。

## 300 という数字

PLATEAU の建物の建築面積の分布である（新サーバの 13,490,667 棟から 72,732 棟を抽出）。

| 位置 | 面積 |
|---|---|
| 中央値 | 67 m² |
| 上位 25% | 107 m² |
| 上位 10% | 174 m² |
| 上位 5% | 255 m² |
| 上位 1% | 800 m² |

300 平方メートル以上の建物は全体の 3.91% で、およそ上位 4% にあたる。
17.3 メートル四方、25 メートルプール 1 面とほぼ同じ広さである。

戸建てとしてはかなり大きい部類に入る。
このくらいの建物であれば部分を持っていてもおかしくない、という判断でこの値を選んだ。

500 平方メートルも検討したが、小さめの工場や校舎を落とすため採らなかった。
200 平方メートルは、同じくらいの大きさの建物が並ぶ集合（e）を 15% 含むため採らなかった。

## 実測

閾値ごとに残る集合の数である。

| 閾値 | 143 都市 (665,464 集合) | 3 都市の標本 (24,178 集合) |
|---|---|---|
| 200 m² | 未測定 | 3,772 (15.6%) |
| 300 m² | 106,470 (16.00%) | 2,200 (9.1%) |
| 500 m² | 67,784 (10.19%) | 1,133 (4.7%) |

標本と全体で割合が違うのは、標本の 3 都市（豊中市、池田市、守口市）が住宅の密集した地域で、大きい建物の割合が低いためである。

標本での類型の内訳である。
閾値 300 で分けたうえで、残りを建物区分と部材の大きさで分類した。

| 分類 | 件数 | 割合 |
|---|---|---|
| 無壁舎を含む（d） | 15,596 | 64.5% |
| 小さい建物の集まり（e） | 4,921 | 20.4% |
| 最大 300 以上（c 候補、条件を満たす） | 2,200 | 9.1% |
| 建物区分が無く判定不能 | 1,049 | 4.3% |
| その他 | 412 | 1.7% |

d と e で 85% を占める。
条件を満たすのは 9.1% である。
「判定不能」は条件を満たさなかったもののうち、建物区分が引けない都市（守口市）の分である。d と e のどちらかにあたる。

## 実装

### 位置

`plateau_importer2postgis.py` の `parse_osm_file_safe` と、`osmfj_plateau_api.py` の `_emit_building_tags` の 2 箇所。

変換器には手を入れない。
`.osm` にはリレーションがそのまま入っているので、取り込みで選ぶだけでよい。

### 取り込み

`4cd2b96` で外した処理を戻し、そこに面積の条件を足す。

1. `type=building` のリレーションを読み、`outline` と `part` のメンバーを集める
2. `part` のメンバーの面積を `.osm` の座標から計算する
3. 最大が 300 平方メートル未満なら、そのリレーションを無視する（現在と同じ挙動になる）
4. 300 平方メートル以上なら、`outline` の way を建物 ID が無くても取り込む
5. `part` のメンバーに `is_part` を立て、`parent_outline_way_id` に外形を入れる

面積は緯度経度の環に対する局所的な正距円筒近似で足りる。
1 メッシュの内部で緯度差が小さく、閾値の判定に必要な精度は十分に出る。

条件を満たさなかったリレーションのメンバーは、現在と同じく独立した建物として取り込む。

### 建物 ID を持たない way の扱い

現在は建物 ID を持たない `building` / `building:part` の way を一律で落としている。
合成外形を取り込むため、ここに例外を作る。

例外の範囲は「条件を満たしたリレーションの `outline` メンバーであること」に限る。
それ以外の ID 無しの way は、これまでどおり落とす。

### 重複排除

外形は建物 ID を持たないが、重複排除の鍵は重心と高さと階数と `building_part` の組み合わせで、建物 ID を使っていない。
外形も他の建物と同じ規則で扱える。

### 配信

`_emit_building_tags` は、メンバーに `building:part=yes` を固定で書いており、DB に入っている型を捨てている。
これを `building:part=<型>` に変える。

無壁舎がリレーションのメンバーになった場合は `building:part=roof` になる。

外形側は現在も `building=<型>` を出しているので、変更しない。

### テスト

- 面積の境界値。最大が 299 なら取り込まず、300 なら取り込むこと
- 部材が 1 本しかないリレーションでも、その 1 本が 300 以上なら通ること（条件を 1 つに保つための意図した挙動である。標本では 24,178 集合中 29 件）
- 条件を満たさなかったリレーションのメンバーが、独立した建物として取り込まれること
- 外形の例外が、リレーションに属さない ID 無しの way を通さないこと
- メンバーの型が `building:part` の値として出ること
- 無壁舎がメンバーのとき `building:part=roof` になること
- 面積の計算が、既知の矩形に対して期待値を返すこと

## 移行

この規則を全 298 都市に効かせるには、都市によって手数が違う。

`.incoming` に残る 150 都市は `.osm` にリレーションが入ったままなので、取り込み直すだけでよい。

新サーバに既に取り込んだ 148 都市は、`.incoming` の中身が消費済みで消えている。
手元から変換をやり直して送り直すことになる。
所要は 3 から 4 時間である。

## 測っていないこと

条件が何件を残すかは 143 都市で測ってある（665,464 集合のうち 106,470 集合）。
測っていないのは、残ったものが実際に c であるかどうかである。

- 閾値 300 は建築面積の分布から置いた数字で、写真と突き合わせて決めたものではない
- 類型の内訳（d が何件、e が何件）は 3 都市の標本でしか出していない。
  建物区分が要るためで、旧サーバの DB には建物区分が入っていない
- 条件を満たしたものが c かどうかは、標本から抜き出した十数件しか見ていない。
  106,470 集合すべてを目で見るのは現実的でないので、抜き取りで確かめるほかない
- 「大きい建物 1 本 + 小さい部材が多数」という形が標本で 129 件残る。
  b の範疇と判断したが、抜き取りで見たのは 4 件である

## 標本について

3 都市の `.osm` と `.gml` は、2026-08-27 の変換で退避されたディレクトリに残っていたものを使った。
リレーションは 24,178 集合、メンバーの way は 92,961 本である。

143 都市の数字は、旧サーバの `plateau_buildings` を `parent_building_id` で集約して求めた。
面積は PostGIS の `ST_Area(geom::geography)` による。

## 追記 (2026-08-29): building=roof が混ざる集合を面積 150 で残す

上の条件だけだと、庇の付いた建物が集合ごと落ちます。
利用者から「`building=roof` と他の値が接している場合はリレーションを外すべきでない」という指摘がありました。

`building=roof` は [2026-08-26 の設計](2026-08-26-walless-building-roof-design.md)で無壁舎に付けた値です。
庇もカーポートも壁がないので、どちらもこの値になります。
値だけでは区別が付きません。

### 実測

再変換済みの 21 都市、リレーション 97,606 件を測りました。

| | 件数 | 割合 |
|---|---|---|
| 300 の条件で残る | 17,621 | 18.1% |
| 300 の条件で落ちる | 79,985 | 81.9% |
| うち `roof` と他の値が混ざっている | 38,452 | 39.4% |

落ちる分の半分近くが、`roof` と他の値の混在です。

### 抜き取り

`roof` 以外の部材の最大面積で 3 つの帯に分け、各帯から抜き取って航空写真とエディタで見ました。

| `roof` 以外の最大面積 | 残すべき | 分けるべき | 判断が付かない | 元データの誤り |
|---|---|---|---|---|
| 150〜300 m² | 6（庇） | 0 | 3 | 1 |
| 100〜150 m² | 4（庇 3、建物の一部 1） | 2（別棟の屋舎） | 4 | 0 |
| 60〜100 m² | 0 | 4（カーポート） | 1 | 0 |

25 件を見て、残すか分けるかを決められたのは 16 件です。
8 件は写真の解像度と撮影時期の都合で判断が付きませんでした。
1 件（盛岡、`roof` 以外の最大 260.6 m²）は写真に建物が写っておらず、元データの誤りか取り壊し済みと判断しました。

150 m² を超える帯では、判定できた 6 件がすべて庇でした。
100 m² を下回る帯では、判定できた 4 件がすべてカーポートでした。
境目は 100〜150 m² の帯にあり、この帯の 6 件は庇 3、建物の一部 1、別棟 2 に割れました。

### 決めたこと

`roof` と他の値が混ざっている集合は、`roof` 以外の部材の最大面積が 150 m² 以上なら取り込みます。

混ざっていない集合は、これまでどおり 300 m² で判定します。
部材がすべて `roof` の集合（カーポートだけ、庇だけ）も、これまでどおり 300 m² で判定します。

面積の比による条件は足しません。
`roof` の面積を `roof` 以外の最大面積で割った値を見たところ、分けるべきと判定した別棟の 0.27 と、残すべきと判定した建物の一部の 0.30 が隣り合っていました。
比では 2 つを分けられません。

### 効果

21 都市での残存が 17,621 件（18.1%）から 25,685 件（26.3%）に増えます。
増える 8,064 件は、混在している 38,452 件の 21.0% にあたります。

再変換のやり直しは要りません。
`.osm` にはリレーションがそのまま入っているので、`plateau_importer2postgis.py` の判定を変えるだけで効きます。

### 実装

`plateau_importer2postgis.py` の relation ループ（`parse_osm_file_safe` 内）に条件を足します。

`_relation_passes_area_gate` そのものは変えず、呼び出し側で部材ごとの建物の型を渡す形にします。
いまは部材の面積の列しか集めていないので、型を集める処理を足します。

1. `raw_way_nd_refs` を作るのと同じ走査で、way ごとのタグを控えます
2. 部材ごとに、面積と `building` / `building:part` の値を組で集めます
3. 値に `roof` と `roof` 以外の両方がある場合は、`roof` 以外の面積の最大が 150 m² 以上かで判定します
4. それ以外の場合は、部材全体の面積の最大が 300 m² 以上かで判定します

閾値は `RELATION_MIN_LARGEST_PART_AREA_M2` の隣に `RELATION_MIXED_ROOF_MIN_OTHER_AREA_M2 = 150.0` として置きます。

### テスト

- `roof` と他の値が混ざり、`roof` 以外の最大が 150 m² のとき取り込むこと
- `roof` と他の値が混ざり、`roof` 以外の最大が 149 m² のとき取り込まないこと
- 混ざっていて `roof` 以外の最大が 149 m² でも、部材全体の最大が 300 m² 以上なら取り込むこと（300 の条件は残るため）
- 部材がすべて `roof` のとき、150 ではなく 300 で判定すること
- `roof` を含まないとき、これまでどおり 300 で判定すること

### 測っていないこと

150 という値は、判定できた 16 件から置いたものです。
帯ごとに 6 件前後しか判定できていないので、120 や 180 のほうが合う可能性は残ります。

帯を細かく分けて抜き取りを増やす方法は考えられますが、写真で判断が付かないものが 25 件中 8 件あり、件数を増やしても精度は上がりにくいと見ています。

増える 8,064 件のうち、実際に庇である割合は測っていません。
150〜300 m² の帯での抜き取り 10 件のうち 6 件が庇、3 件が判断不能、1 件が元データの誤りでした。
